# 이미지 본문 판독

`csv/merged.csv` 에서 **본문이 그림 한 장인 공고**만 골라 그림을 읽고, `기술스택`·`자격요건`·
`우대사항` 을 채운다. 셋 중 하나도 못 얻으면 그 공고는 버린다.

수집 단계는 본문이 그림이면 `기술스택` 칸에 **그림 주소**를 남긴다 — 수집은 순수 HTTP 만
하기로 했고(`docs/convention/06-decisions.md` 의 D-13), 주소를 읽는 쪽이 이 단계다.

## 왜 필요한가

지난 `merged.csv` 325행 기준 **29건(9%)** 이 그림 본문이다. 사이트마다 편차가 크다.

| 사이트 | 그림 본문 | 그 사이트 전체 |
|---|---|---|
| 잡코리아 | 20건 | 55행 중 (**36%**) |
| 사람인 | 9건 | 142행 중 (6%) |
| 나머지 넷 | 0건 | — |

잡코리아는 셋에 하나가 그림이다. 안 읽으면 그 사이트를 3분의 1만 쓰는 셈이다.

## 두 가지로 쓴다

```bash
python3 job_crawling_ochestrator.py   # 수집부터 이미지 판독까지 한 번에
python3 job_image_process.py          # 이미 있는 csv/merged.csv 의 그림만 다시 처리
```

수집이 8~10분인데 이미지 쪽만 다시 돌려 보고 싶을 때가 반드시 온다 — 프롬프트를 고쳤을 때,
모델을 바꿔 볼 때, 캐시를 지우고 다시 읽을 때. 그때마다 여섯 사이트를 다시 긁을 이유가 없다.

`job_image_process.py` 는 **혼자서도 도는 엔트리포인트**다. 오케스트레이터는 이것을 **자식
프로세스로** 부른다 — 불러들이지(import) 않는다. 각 스크래퍼를 프로세스로 나눠 부르는 이유와
같다(`sys.path` 오염, `ORCHESTRATOR.md` 의 "왜 프로세스를 나누나"). 불러들이면 같은 함정을
새로 만든다.

**`csv/merged.csv` 는 고치지 않는다.** 이 단계는 행을 **없애기** 때문에, 제자리에서 고치면
없어진 행의 원본이 어디에도 안 남는다. 대신 `csv/merged_read.csv` 를 새로 낸다. 두 파일을
URL 로 맞춰 보면 이 단계가 무엇을 했는지 전부 나온다.

| | |
|---|---|
| 양쪽에 있고 값이 다르다 | 채운 행 |
| `merged.csv` 에만 있다 | 버린 행 |
| 양쪽이 같다 | 안 건드린 행 |

## 한 건이 지나는 길

```
merged.csv 의 행
   │
   ├ 기술스택이 http 로 시작하지 않는다 ──────→ 그대로 통과
   │
   ├ 이 공고의 주소 목록이 캐시에 있다 ────────→ 캐시 값으로 채움. 부르지 않는다
   │
   └ 내려받기 → 껍데기 거르기 → 자르기 → claude -p → 채우거나 버리기
```

`기술스택` 칸에 `http` 조각이 하나라도 있으면 그림 본문으로 본다. **칸 안 어디에 있든
찾는다.**

처음에는 칸이 `http` 로 **시작하는지**만 봤다. "주소와 진짜 기술이 섞인 행은 0건" 이라는
실측을 근거로 삼았는데 **그 실측이 틀렸다** — `http` 로 시작하는 행만 골라 놓고 그 안에서
섞인 것을 찾는 순환 논증이었고, 기술이 먼저 오는 행은 표본에 애초에 안 들어갔다.

사람인은 기술을 먼저 주고 주소를 뒤에 붙인다.

```
C++, C, Java, PyTorch, https://pds.saramin.co.kr/…/recruit.png
```

실제 데이터에서 주소가 든 **175행 중 73행(42%)** 이 이 모양이라 판독 단계를 통째로
지나갔다. 그 공고들의 내용은 그림 안에 있는데 아무도 안 읽었고, 주소는 `기술스택` 칸에
그대로 남아 다음 단계가 기술 이름으로 읽을 참이었다.

그래서 **기술스택도 덮지 않고 보강한다.** 수집 단계가 이미 찾아 둔 기술은 그대로 두고,
그림에서 읽은 것 중 없는 것만 더하고, 주소는 걷어낸다.

`자격요건`·`우대사항` 은 이미 차 있을 수 있다(사람인 모집조건 표에서 온 값). 그건 **지키고
없는 것만 더한다** — 기존 글을 줄 단위로 쪼개, 글머리표와 공백·문장부호를 지우고 소문자로
맞춘 뒤, 읽어 낸 항목이 완전히 같거나 기존 글 안에 통째로 들어 있으면 건너뛴다. **편집거리는
안 쓴다** — `REST`/`Rust` 를 같은 것으로 볼 위험이 여기서도 같다(D-04). 애매하면 더하는
쪽으로 기운다. 중복은 눈에 거슬리는 정도지만, 빠뜨린 자격요건은 그 공고를 잘못 판단하게
만든다.

## 왜 잘라야 하는가

세로가 가로의 **2.4배**를 넘으면 자른다. 실측한 33개 주소 중 **22개(67%)** 가 해당하고,
가장 긴 것은 `1505 × 21708` 이다.

통째로 넣으면 긴 변에 맞춰 축소돼 작은 글씨가 뭉갠다. 같은 그림(1505×21708)·같은 모델
(sonnet)로 재 봤다.

| | 기술스택 | 자격요건 | 우대사항 | 시간 |
|---|---|---|---|---|
| 통째로 | 24개 | **0개** | **0개** | 32.7초 |
| 7조각 | 18개 | **5개** | **6개** | 23.1초 |

시간은 참고만 한다 — 통째로 쪽은 `--max-turns 4` 로 프롬프트도 조금 달리해서 잰 값이라
조각 쪽과 조건이 안 맞는다. **이 표의 요점은 초가 아니라 칸 수다.** 자르지 않으면
자격요건·우대사항이 아예 안 나온다는 것, 그게 실측이 보여 주는 것이다.

그림에는 자격요건 5개와 우대사항 6개가 또렷이 있다. 눈으로 확인했다. **통째로 넣으면 이
멀쩡한 공고가 버려진다** — 버리는 규칙이 있는 설계에서 이런 거짓 실패는 조용히 데이터를
없앤다. 모델을 바꿔 풀 문제가 아니다 — 축소된 픽셀에 글자가 없으면 opus 도 못 읽는다.

**등분하지 않는다.** 등분하면 글줄 한가운데를 자른다. 대신 가로 한 줄이 통째로 무늬 없는
곳(여백)을 찾아 그 한가운데를 자른다. 실측한 `1505×21708` 그림에 20px 이상 여백 띠가
**126개**, 띠 없는 최장 구간이 **1,794px** 로 목표 높이(3,612px)보다 한참 짧아 늘 자를
자리를 찾았다(강제로 자른 곳 0건).

여백을 못 찾으면(빽빽한 표 같은 것) 그 자리에서는 **겹쳐서** 자른다 — 잘린 줄이 옆 조각에
온전히 한 번 더 나오게. 중복은 위의 대조 규칙이 걸러 준다.

여백 판정은 한 줄에서 200칸만 찍어 보고 정한다(전수는 21,708줄에는 느리다). 그런데 표본
칸 사이에만 글자가 걸리면 그 줄을 잘못 "무늬 없음" 으로 본다 — 실측한 그림에서 이렇게
잘못 잡힌 줄이 972/21708행(4.5%), 최대 192px 연속으로 나왔다. 그래서 **자르기 직전에** 그
한 줄만 전수로 다시 확인한 뒤에야 자른다. 후보를 놓치면 다음으로 두꺼운 후보를, 그것도
없으면 강제/겹침 경로로 넘어간다.

순수 파이썬(Pillow)이다. **자르기를 판단하는 에이전트를 두지 않는다** — 자르는 자리는
결정적으로 정해진다.

## 모델은 sonnet — 병목은 모델이 아니라 입력이었다

같은 조각 입력으로 나란히 돌렸다. **결과가 글자 하나까지 같았다.**

| | sonnet | opus |
|---|---|---|
| 결과 | 기술 18 · 자격 5 · 우대 6 | 기술 18 · 자격 5 · 우대 6 (동일) |
| 비용 | **$0.162** | $0.399 (2.5배) |

이 일은 추론이 아니라 또렷한 이미지에서 글을 옮겨 적는 것이다. 그 병목은 자르기로 이미
풀렸다. 근거가 공고 한 건이므로 **모델은 설정으로 바꿀 수 있게 둔다**(`IMAGE_MODEL`).
어려운 이미지(저해상도·손글씨풍·복잡한 표)에서 sonnet 이 눈에 띄게 놓치면 재 보고 그
측정으로 기본값을 옮긴다.

## 병렬은 4개에서 시작한다

**처음 근거는 틀렸다.** 설계할 때 "한 건이 87k 토큰을 쓰니 동시에 던지면 분당 한도에
걸린다" 고 적었는데, **분당 토큰 한도는 API 이야기다.** `claude -p` 는 API 키가 아니라
구독 계정(OAuth)으로 붙고, 거기에 그런 분당 한도가 있는지 확인한 적이 없다. 남의 개념을
갖다 붙인 것이다.

**남는 이유는 둘이고, 둘 다 한도와 무관하다.**

`claude -p` 는 얇은 HTTP 호출이 아니라 **매번 Claude Code 프로세스가 통째로 뜬다.** 수십 개를
동시에 띄우면 이 기계가 먼저 힘들어진다.

그리고 무엇이 됐든 막히면 **동시에 던진 만큼이 한꺼번에 실패한다.** 이 단계는 "못 뽑으면
버린다" 라서 실패의 폭이 곧 위험이다. 아래 "버림과 실패" 구분이 그걸 막지만, 애초에 안 겪는
편이 낫다.

**실측** — 같은 조건(캐시·CSV 지우고 시작)으로 전체를 세 번 돌려 쟀다.

| 동시 | 이미지 판독 | 전체 실행 | 건당 실효 | 못 읽음 | 직전 대비 |
|---|---|---|---|---|---|
| 4 | 559초 | 19.3분 | 5.4초 | 2건 | — |
| 8 | 305초 | 15.1분 | 3.0초 | 3건 | −45% |
| **16** | **185초** | **13.0분** | **1.8초** | 2건 | −39% |

**16에서 곡선이 꺾인다.** 두 배로 올리면 이상적으로 −50%인데 4→8 은 −45%(효율 90%),
8→16 은 −39%(효율 78%)였다. 이 기계가 **코어 10개**라 프로세스 16개가 서로 밀어내기
시작한 것이다. 메모리는 문제가 아니었다 — 16개가 약 4.4GB를 썼다(한 개당 약 278MB).

32로 올리면 계산상 1분쯤 더 벌지만 권하지 않는다. 코어의 세 배를 띄우는 데다, 전체
13분 중 이미지가 이미 **24%**뿐이고 나머지는 사람인 수집 9.9분이다. **더 짜낼 곳은
여기가 아니다.**

기본값 4 는 안전한 출발점일 뿐 상한이 아니다. `.env` 의 `IMAGE_CLAUDE_WORKER` 로 올린다.

한 가지 밝혀 둘 것 — **재시도는 조용하다.** 1차에 실패하고 2차에 통과하면 화면에 아무것도
안 남는다. 그래서 "한 번도 안 막혔다" 는 말은 이 로그로 할 수 없고, "최종 실패가 없었다"
까지만 말할 수 있다.

## 경고는 막대 위로 올린다

경고는 stderr 로 나가는데 진행 막대도 stderr 를 쓴다. 그대로 두면 막대가 덮어써서 실행
로그에 `warnings.warn(` 마지막 줄만 남는다 — **실제로 그렇게 한 건을 잃었고 어느 그림
때문인지 끝내 못 찾았다.**

미관 문제가 아니다. Pillow 는 픽셀이 **8,900만을 넘으면 경고만 내고 그림은 읽는다**
(오류는 그 두 배인 1억 7,900만부터). 그 구간의 그림은 조용히 지나가므로, 경고가 묻히면
우리가 무엇을 아슬아슬하게 읽고 있는지 알 방법이 없다.

```
경고: DecompressionBombWarning: Image size (108000000 pixels) exceeds limit of
      89478485 pixels … — https://pds.saramin.co.kr/…/huge.png
```

어느 그림에서 났는지도 함께 찍는다 — 실 하나가 지금 다루는 주소를 적어 두고 경고가 날 때
읽는다. `warnings.catch_warnings` 는 안 쓴다. 전역 상태를 건드려서 실 여럿이 함께 돌면
서로를 덮어쓰는데, 여기는 동시 16개까지 돈다.

## 버림과 실패를 가른다 — **이 설계에서 가장 위험한 곳**

버리는 규칙이 있는데 실패 종류를 안 가르면 **우리 쪽 사고로 멀쩡한 공고를 없앤다.**

| 무슨 일 | 버리나 | 캐시에 넣나 |
|---|---|---|
| 모델이 답했는데 셋 다 비었다 | **버린다** | 넣는다 |
| 껍데기 이미지뿐이다 (열렸는데 1×1) | **버린다** | 넣는다 |
| 내려받기 실패 · **이미지가 안 열림** | 안 버린다 | 안 넣는다 |
| `claude -p` 시간 초과 · 비정상 종료 | 안 버린다 | 안 넣는다 |
| 답을 JSON 으로 못 읽었다 | 안 버린다 | 안 넣는다 |

아래 셋은 **우리가 못 읽은 것이지 공고에 내용이 없는 게 아니다.** 그런 행은 원래 모습
그대로(기술스택에 주소가 남은 채) `merged_read.csv` 에 남기고, 실행이 끝날 때 몇 건인지
찍는다. 캐시에 안 넣으므로 다음 실행에 다시 시도한다.

반대로 "셋 다 비었다" 는 **결과이지 실패가 아니다.** 캐시에 넣는다 — 안 넣으면 쓰레기
이미지를 30일 동안 매 실행 다시 읽는다. **판정 기준은 최종 상태가 아니라 이미지에서 얻은
것이다** — 기존 자격요건이 차 있어도 이미지에서 셋 다 못 얻었으면 버린다.

껍데기 판정은 `가로 < 100` 이거나 `세로 < 100` 인 그림뿐이다. 주소 33개를 전부 내려받아
재 본 결과 여기 걸리는 것은 `blank.png`(1×1, 73바이트) 하나뿐이었다. 크기로 더 욕심내지
않는다 — 사람인 기본 템플릿(`it1.webp`, 1720×760) 같은 것은 크기로는 못 가린다. 그건 위
표의 "셋 다 비었다" 로 걸린다.

**"열었는데 작다" 와 "아예 못 열었다" 는 다른 사실이다.** 200 으로 받았는데 내용이 안내
페이지 HTML 이거나, AVIF·HEIC 처럼 Pillow 가 기본으로 모르는 형식이면 `Image.open` 이
터진다. 그것을 껍데기로 세면 그 공고는 **버려지고 그 버림이 캐시에 남아 영영 다시
시도하지 않는다.** 그래서 `is_junk` 는 **크기만** 판정하고, 못 여는 것은 내려받기 실패와
같은 `FetchError` 로 올린다 — 위 표의 셋째 줄이다.

**재시도는 내려받기와 모델 호출에 각각 한 번씩.** 처음에는 비싼 모델 호출에만 걸어 뒀는데
**거꾸로였다** — 전체 실행 두 번에서 최종 실패 3건 중 2건이 그림 서버가 연결을 끊은 것이었고
모델 호출은 한 번도 안 끊겼다. 그 그림들은 나중에 단독으로 받으면 멀쩡히 받힌다. 내려받기는
값이 거의 안 드니 한 번 더 두드리는 비용이 없다.

**판독에는 안 건다.** 받아졌는데 안 열리는 파일은 같은 바이트를 다시 열어 봐야 결과가 같다 —
2억 3천만 픽셀짜리 그림이 그랬다. 두 번째도 실패하면 포기하되 버리지 않는다.

**단계 자체가 못 도는 경우** — `claude` 명령이 없거나 `csv/merged.csv` 가 없으면
`merged_read.csv` 를 **아예 안 만들고 종료 코드 1** 을 낸다. 반쯤 처리된 파일을 남기면
다음 단계가 그걸 완성품으로 착각한다. `merged.csv` 는 이미 나와 있으니 걷은 것은 잃지
않는다.

## 캐시

없으면 매 실행마다 같은 이미지를 다시 읽는다. 사이트별 CSV 가 30일 누적이라 같은 공고가
30일 동안 계속 대상에 잡힌다 — 한 달이면 같은 그림을 서른 번 읽는다.

```
job_sites/_common/cache/image_reads.json
  { "https://…/ahnlab_0903_01.jpg https://…/ahnlab_0903_02.jpg": {
      "기술스택": [...], "자격요건": [...], "우대사항": [...],
      "읽은날": "2026-09-07", "모델": "sonnet" } }
```

### 열쇠는 **공고의 주소 목록 전체**다 — 낱장이 아니다

한 공고의 그림들은 **합쳐서 한 번** 읽는다. 그러니 그 답은 그 조합의 답이지 낱장의 답이
아니다. 낱장 주소를 열쇠로 쓰면 같은 그림을 쓰는 다른 공고가 **남의 답을 자기 것으로 받아
간다** — 이름은 B 회사인데 자격요건은 A 회사인 행이, 버려지지도 않고 캐시에까지 남는다.

가정이 아니다. 실제로 걷은 데이터에서 `…/hiring/images/blank.png` 를 서로 다른 두 회사가
쓰고 있었고, `…/images/template/toptype/it1.webp` 는 사람인 공용 템플릿이라 성격상 여러
공고가 나눠 쓴다.

그래서 열쇠는 **주소들을 차례까지 지켜 공백 하나로 이어 붙인 것**이다. 주소에는 공백이
못 들어가므로(RFC 3986 — `%20` 으로 적힌다) 어디서 끊긴 것인지 헷갈리지 않고, 해시와
달리 캐시 파일을 열어 보면 어느 공고의 답인지 눈으로 알아볼 수 있다. **공고 하나에 열쇠
하나, 답 하나.**

덤으로, 그림 여러 장 중 한 장만 캐시에 없다고 전부 다시 받아 읽던 일도 없어진다 — 애초에
낱장으로 맞춰 보지 않는다.

**옛 캐시 파일의 낱장 열쇠는 전부 빗나간다.** 첫 실행은 캐시 없이 도는 셈이고, 그 뒤로는
공고 단위로 다시 쌓인다. 지워도 되고 그냥 둬도 해가 없다 — 캐시는 편의지 진실이 아니다.

`**/cache/` 는 이미 gitignore 돼 있다. 파일이 깨져 있으면 무시하고 새로 읽는다 — 캐시
때문에 단계가 멎으면 안 된다.

**두 번째 실행부터 이 단계는 수 초에 끝나고 돈이 안 든다.**

## 설정

기본값은 코드에 있고, `.env` 에 적으면 그것을 쓴다. **아무것도 안 적어도 돈다** — `.env` 는
"여섯 사이트가 함께 쓰는 검색 조건" 한 벌이고 이 셋은 성격이 다르다. 조건은 없으면
멈추지만(D-08), 이건 기본값이 있다.

| 항목 | 기본 | 뜻 |
|---|---|---|
| `IMAGE_MODEL` | `sonnet` | `claude -p --model` 에 넘길 값 |
| `IMAGE_CLAUDE_WORKER` | `4` | 동시에 띄울 `claude -p` 개수 |
| `IMAGE_TIMEOUT` | `300` | 한 건의 시간제한(초) |

## 종료 코드

오케스트레이터가 자식으로 부르므로 여섯 스크래퍼와 **같은 계약**을 물려받는다.
실행 자물쇠도 같은 것을 쓴다 — `job_sites/_common/runlock.py` 의 `guarded()`. 자물쇠는
`csv/.image_process.lock` 에 둔다.

| 코드 | 뜻 | 성패 |
|---|---|---|
| 0 | 정상 (대상이 0건이어도 정상이다) | 성공 |
| 1 | 설정 오류 — `merged.csv` 가 없다, `claude` 를 못 찾는다 | 실패 |
| 2 | **아무것도 못 해냈다** — 못 읽은 것만 있고 건진 것이 하나도 없다 | 실패 |
| 3 | 이미 돌고 있음 | 실패 |

**`4`(조건이 넓어 건너뜀)는 안 쓴다.** 이 단계에는 건너뛸 조건이 없다.

**`2` 는 "하나도 못 해냈다" 일 때만 낸다.** 캐시 적중·채움·버림은 전부 해낸 것으로 센다.
자리 잡힌 뒤에는 거의 모든 건이 캐시 적중이라, 캐시를 빼고 세면 **새로 들어온 공고 하나가
시간 초과만 나도 실행 전체가 실패**가 된다(캐시 28 + 못읽음 1 → `2`). 그러면 오케스트레이터가
여덟 분짜리 수집을 실패로 적는다. 못 읽은 건수는 어차피 요약에 찍히고, 그 행은 그대로 남아
다음 실행에 다시 시도한다.

뜻풀이 문구는 오케스트레이터가 따로 갖고 있다 — `job_crawling_ochestrator.py` 의
`IMAGE_EXIT_MEANING`. 스크래퍼 표(`EXIT_MEANING`)를 빌려 쓰면 이 단계의 `2` 가 "차단이거나
상세를 못 받음" 으로 찍힌다. 이 단계는 사이트를 긁지 않는다.

## 파일 구성

```
job_image_process.py        ← 엔트리. 혼자서도 돈다 (루트에 있다)
image_process/
├── config.py   모델 · 동시 수 · 시간제한 · 자르기 비율
├── fetch.py    내려받기 · 껍데기 판정
├── slicing.py  여백 찾기 · 자르기
├── reader.py   claude -p 호출 · 출력 파싱
├── fill.py     기존 값과 대조해 더하기 · 버림 판정
└── cache.py    공고별 판독 캐시 (열쇠는 주소 목록 전체)
```

`slicing.py` 다 — `slice.py` 는 파이썬 내장 이름이라 피했다.

`image_process/` 는 `job_sites/_common/` 에 넣지 않는다. `_common` 은 **사이트들이 나눠
쓰는 계층**이고, 이 단계는 사이트를 모르고 사이트도 이 단계를 모른다
(`docs/convention/01-architecture.md` 의 import 방향). 다만 `_common` 을 **쓰기는 한다** —
`store.COLUMNS`(스키마)와 `runlock.guarded()`, `env` 읽기. 오케스트레이터도 이미 그렇게
쓴다.

**Pillow 가 새 의존성이다.** 지금까지 `requests` `tqdm` `python-dotenv` 뿐이었다.

```bash
.venv/bin/pip install Pillow
```

## 테스트

네트워크도 `claude` 도 타지 않는다. 호출 함수를 가짜로 바꿔 넣고, 이미지는 **Pillow 로 그
자리에서 그린다** — 5MB 짜리 실물을 저장소에 넣을 수 없고, 넣어도 OCR 결과는 시험할 수
없다. 시험할 수 있는 것만 시험한다.

```bash
.venv/bin/python3 tests/run.py       # 루트에서. 오케스트레이터 테스트와 같은 자리에 있다
```

| 갈래 | 무엇 |
|---|---|
| 자르기 | 여백에서 잘리는가 · 여백이 없으면 겹쳐 자르는가 · 가로가 더 긴 이미지는 안 자르는가 · 비율 경계값 |
| 껍데기 | 1×1 은 걸러지는가 · 100×100 은 통과하는가 · 조각 0개면 바로 버리는가 |
| 판정 | 셋 다 비면 버린다 · 하나라도 있으면 살린다(셋 각각) · 캐시에 넣는 것과 안 넣는 것 |
| 실패 | 호출 실패는 **안 버린다** · **못 여는 파일도 안 버린다** · 캐시에 안 들어간다 · 내려받기와 호출에 각각 재시도 한 번 · 판독은 재시도 안 함 |
| 파싱 | JSON 앞의 경고 줄 · 앞뒤에 말이 붙은 출력 · 아예 JSON 이 아닌 출력 |
| 대조 | 같은 항목은 안 더한다 · 기존 글에 통째로 든 항목은 안 더한다 · 글머리표만 다른 것 |
| 캐시 | 적중하면 호출 0회 · **공용 그림을 쓰는 다른 공고에 새지 않는다** · 차례도 열쇠의 일부 · 옛 낱장 열쇠는 빗나간다 · 파일이 깨져 있으면 무시하고 새로 읽는다 |
| 한 판 전체 | `_run()` 을 임시 CSV 로 통째로 돌린다 — **버린 행 하나가 나머지 자리를 밀지 않는가** · 캐시 적중이 있으면 `2` 가 아니다 · 하나도 못 해내면 `2` |

**가장 중요한 것은 "실패는 버리지 않는다"** 다. 그게 뚫리면 우리 사고로 데이터가 조용히
사라진다.

`_run()` 은 **반드시 통째로 돌려 본다.** 행을 골라 처리하고 없어진 것을 뺀 채 다시 쓰는
그 재조립은 조각 함수를 아무리 시험해도 안 돈다 — 거기서 틀어지면 멀쩡한 공고가 남의
자리로 가거나 사라진다.

## 되돌릴 조건

- 그림 본문 비율이 5% 아래로 떨어지면 이 단계를 둘 값이 없다 (D-13 의 조건과 같다).
- 어려운 이미지(저해상도·손글씨풍·복잡한 표)에서 sonnet 이 눈에 띄게 놓치면 `IMAGE_MODEL`
  로 바꿔 재 보고, 그 측정으로 기본값을 옮긴다.
- `IMAGE_CLAUDE_WORKER` 를 올려 재 본다. 동시 4개는 실측으로 문제없었다. **얼마로 올리든 실패와
  버림을 가르는 규칙은 그대로 둔다** — 그게 없으면 한 번 막힐 때 데이터가
  사라진다.
