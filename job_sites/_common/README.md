# 채용 사이트 공통 계층

여러 채용 사이트에서 뽑은 기술 이름을 **한 표준 이름으로 모으는** 사전과 함수.
사이트별 스크래퍼(`../wanted/` 등)가 여기를 참조한다.

## 왜 필요한가

사이트마다 자기 어휘로 기술 이름을 뱉는다. Wanted 는 `Apache Kafka` `Spring Framework` `GCP`,
다른 곳은 `Kafka` `Spring` `Google Cloud` 라고 적을 수 있다. 그대로 두면 CSV 를 합쳤을 때
같은 기술이 여러 이름으로 갈린다.

## 파일

| 파일 | 무엇 |
|---|---|
| `tech_corpus.json` | **표준 이름 + 분류.** 349개. `name` `kind` `devtypes` `source` |
| `tech_aliases.json` | 별칭 → 표준 이름 (`GCP`→`Google Cloud`) |
| `tech_blocklist.txt` | 산문 매칭에서 걸러 낼 말 (`IR` `SaaS` `Spa` `TPM`) |
| `tech_ko_allowlist.txt` | 산문에서 찾을 한글 기술어 |
| `dictionaries.py` | **사전 파일을 읽는 유일한 곳.** 형식을 아는 데가 여기 하나여야 사이트를 붙일 때 파싱이 복제되지 않는다 |
| `normalize.py` | `canonical()` `kind_of()` — 이름을 표준 표기로 |
| `skills.py` | **산문에서 기술 이름을 찾는 엔진.** 사이트는 자기 어휘만 넘긴다 |
| `store.py` | CSV 스키마 13컬럼 · 누적 병합 · 30일 보존 · 원자적 쓰기 |
| `runlock.py` | 실행 락. 겹쳐 도는 실행을 막는다. **종료 코드 3** 을 여기서 정한다 |
| `roles.json` | **표준 직무 이름 16개**와 별칭. `.env` 의 `JOB_ROLES` 에 적을 수 있는 값 |
| `roles.py` | `JOB_ROLES` → 그 사이트 코드. 사이트는 자기 대응표 경로만 넘긴다 |
| `outcome.py` | 수집이 온전했는가의 판정. **종료 코드 2** 를 여기서 정한다 |
| `env.py` | **`.env` 를 읽는 유일한 곳.** 주석 처리·콤마 목록·셸 환경변수 차단 |
| `sections.py` | 본문을 지원자격·우대사항으로 가르는 규칙 |
| `html_text.py` | HTML → 글. 줄바꿈과 목록 표시를 살린다 |
| `corpus_candidates.py` | 표준 이름으로 못 푼 기술 이름을 모아 둔다. 사람이 보고 사전으로 옮긴다 |

**`_common` 은 사이트를 모른다.** 여기에는 표준 이름과 규칙만 있고, 어느 이름이 어느
코드인지는 각 사이트의 `tags/` 에 있다 — `_common` 이 사이트 코드를 알면 그건 공통이
아니다 (`docs/convention/01-architecture.md` 의 import 방향).

**`_common` 의 테스트는 `saramin/tests/` 에 있다.** 어느 한 사이트에 붙여 두면 그 사이트를
지웠을 때 시험도 같이 사라진다.

## 쓰는 법

```python
from _common.normalize import canonical, kind_of
from _common.skills import build_matcher

canonical("Apache Kafka")      # -> "Kafka"
canonical("Quarkus")           # -> "Quarkus"   사전에 없으면 그대로 둔다
kind_of("Kafka")               # -> "tool"

matcher = build_matcher(site_terms=my_site_skill_names())
matcher.find("Java Spring 기반, Docker/K8s")   # -> ['Java', 'Spring', 'Docker', 'Kubernetes']
```

**사이트를 새로 붙일 때 여기서 가져갈 것**은 셋이다 — 표기 정규화(`normalize`),
기술 찾기(`skills.build_matcher`), 저장(`store` + `runlock`). 사이트가 직접 만드는 것은
자기 스킬 어휘와 응답 구조를 푸는 코드뿐이다.

## 재실행 — 덮어쓰지 않고 쌓는다

파이프라인은 주기로 돈다. 매 실행이 파일을 갈아엎으면 마감돼 내려간 공고가 흔적 없이
사라진다 (실측: 몇 시간 만에 공고 하나가 `status=close` 로 내려갔다).

`store.merge()` 가 공고 URL 을 키로 세 갈래를 나눈다.

| | 어떻게 |
|---|---|
| 처음 본 공고 | 추가하고 `최초수집일` `최종확인일` 을 오늘로 |
| 이번에도 본 공고 | 내용을 최신으로 갈아 끼우고 `최종확인일` 만 오늘로. **`최초수집일` 은 지킨다** |
| 이번에 안 보인 공고 | 남겨 둔다. `최종확인일` 이 멈춰서 내려갔음이 드러난다 |
| **30일 넘게 안 보인 공고** | **뺀다.** 안 그러면 지원할 수도 없는 공고가 끝없이 쌓인다 |

CSV 스키마는 13컬럼이다. 앞 11개는 공고에서 나오고, 뒤 2개는 쌓아 둔 파일과 맞대야 나온다.

```
기업명, 공고명, 마감일, 지원자격, 우대사항, 경력, URL, 연봉, 기술스택, 근무지, 사이트명, 최초수집일, 최종확인일
```

쌓는 구조가 되면 쓰기 사고의 대가가 커진다. 덮어쓰기 시절에는 다시 돌리면 그만이었지만
이제 파일 하나에 이력이 전부 들어 있다. 그래서 둘을 함께 둔다.

- **원자적 쓰기** — 임시 파일에 다 쓰고 `os.replace` 로 바꿔치기한다. 도중에 죽어도 이전 파일이 남는다
- **실행 락** — cron 이 겹쳐 두 실행이 읽고-고치고-쓰면 한쪽 결과가 조용히 사라진다.
  죽은 실행이 남긴 락은 스스로 걷어낸다 (pid 를 적어 두고 살아 있는지 본다)

보존 기간은 `store.RETENTION_DAYS = 30`. 정확히 30일째는 남고 31일째부터 뺀다.
`merge(..., retention_days=N)` 으로 사이트마다 달리 줄 수도 있다.

**날짜를 모르는 행은 지우지 않는다.** 이력 컬럼이 없던 시절 CSV 에서 올라온 행이 그렇다.
모르는 것을 오래됐다고 단정하면 지울 이유가 없는 공고를 지운다. 다음 수집에서 그 공고가
보이면 날짜가 붙고, 그때부터 정상적으로 세어진다. 오늘이 언제인지 못 읽는 경우에도
만료 판단 자체를 하지 않는다 — 지우는 판단에 "모르겠으면 지운다" 는 있을 수 없다.

## corpus 는 어디서 왔나

`tech_corpus.json` 의 349개는 두 갈래가 합쳐진 것이다. **이미 합쳐져 파일에 들어 있고,
다시 만들 일은 없다.** 이 저장소만 클론하면 그대로 돈다 — 바깥 경로를 보는 코드는 없다.

| 출처 | 개수 | 무엇 |
|---|---|---|
| `source: "devskill"` | 271 | DevSkill 프로젝트의 온톨로지 (`modern_tech_augmentation.csv` + `frameworks_ontology.json`). `kind` 와 `devtypes` 가 여기서 왔다 |
| `source: "observed"` | 78 | 채용공고에서 실측된 것. 씨앗 271개로는 등장 기준 33%를 못 덮었다 (`GitHub` `Spring` `REST API` `Google Cloud` `NestJS` `Grafana` `RDBMS` `CUDA` 한글 항목 …) |

`kind` 는 DevSkill 의 6종(`language` `framework` `library` `tool` `platform` `database`)에
두 가지를 더했다. 채용공고에는 제품이 아닌 것도 기술 요구로 적힌다.

- `concept` — 설계·방법론 (`OOP` `TDD` `마이크로서비스`)
- `protocol` — 통신 규약·표준 (`TCP` `HTTP` `OAuth`)

### 기술을 하나 더 넣으려면

`tech_corpus.json` 의 `tech` 배열에 한 항목을 손으로 더한다. 스크립트가 필요할 만큼
복잡한 일이 아니다.

```json
{ "name": "Quarkus", "kind": "framework", "devtypes": [], "source": "observed" }
```

`name` 은 **표준 표기**다 — 산문에서 다른 표기로 나온다면 `tech_aliases.json` 에
`"쓰이는 표기": "Quarkus"` 를 함께 넣는다.

## 한글은 낱말 경계가 없다 — 목록이 아니라 규칙으로 푼다

`가상화폐` 안에 `가상화` 가, `컨테이너선` 안에 `컨테이너` 가 들어 있다. 영어처럼
`\b` 로 자를 수 없다.

처음에는 충돌하는 복합어를 파일에 적어 막았다(`가상화폐` `컨테이너선` …). **그건 잘못된
설계였다.** 충돌 복합어는 **열린 집합**이라 끝이 없다 — 관측한 것만 막고 다음 것은 그대로
통과시킨다. 실제로 그 목록은 공고 600건을 훑는 동안 **한 건도 걸러내지 못했다.**
거기 적힌 네 낱말이 그 표본에 안 나왔기 때문이다. 새 낱말이 오면 그대로 뚫린다.

지금은 **닫힌 부류**로 판정한다. 한국어에서 낱말 뒤에 붙는 조사·어미·접미사는 문법이 정해
놓은 유한한 집합이고, **새 기술이 나와도 늘어나지 않는다.**

| 본문 | 뒤에 오는 것 | 판정 |
|---|---|---|
| `컨테이너를` | `를` — 조사 | 낱말이 끝났다 → 통과 |
| `분산 처리한` | `한` — 어미 | 낱말이 끝났다 → 통과 |
| `컨테이너화` | `화` — 접미사 | 낱말이 끝났다 → 통과 |
| `컨테이너 오케스트레이션` | 공백 | 낱말이 끝났다 → 통과 |
| `컨테이너선` | `선` — 셋 다 아님 | 다른 낱말이다 → 거부 |
| `가상화폐` | `폐` — 셋 다 아님 | 다른 낱말이다 → 거부 |

`_common/skills.py` 의 `KOREAN_TRAILERS` 가 그 부류다.

**검증**: 공고 600건에서 옛 방식과 **똑같이 394회** 매치한다 — 실제 데이터로는 손실이 없다.
그러면서 한 번도 적어 둔 적 없는 충돌(`가상화학` `컨테이너박스` `머신러닝머신` `딥러닝쿠키`)을
거부한다. 목록 방식은 그것들을 전부 통과시켰다.

형태소 분석기(kiwipiepy)도 재 봤다. 정확도는 같고(600건 393~394회) 공고당 3.2ms 가 더 들며
의존성이 하나 는다. 이득이 없어 쓰지 않았다.

**이 규칙은 놓치는 쪽으로 틀린다.** `딥러닝모델` 처럼 뒤에 다른 명사가 붙으면 거부한다.
목록은 반대로 **틀린 데이터를 넣는 쪽으로** 틀렸다. 둘 중에는 놓치는 편이 낫다.

### 남는 불확실성 — `tech_ko_allowlist.txt`

경계 판정은 규칙이 됐지만, **어느 한글 낱말이 기술어인가**는 여전히 목록이다. 이건 규칙으로
만들 수 없다 — corpus 에 `운영` `감사` `보증` 같은 일반명사가 한글 스킬로 들어 있어서,
"corpus 에 있으면 기술어" 라고 하면 오탐이 쏟아진다. `tech_blocklist.txt` 와 같은 성격의
**판단**이다.

다만 실패 방향이 다르다. 목록에 없는 기술어는 **누락**될 뿐 틀린 값이 들어가지는 않는다.
경계 판정의 실패(오탐)와 달리 안전한 쪽이다.

## 편집거리 매칭을 쓰지 않는 이유

DevSkill 에는 `canonicalize()`(rapidfuzz, threshold 70~85)가 있지만 **가져오지 않았다.**
채용공고에서 뽑은 이름에 걸어 보니 다른 기술로 붙었다.

| 입력 | fuzzy 결과 | 점수 | 실제 |
|---|---|---|---|
| `REST` | `Rust` | 75 | 전혀 다른 것 |
| `Apache Kafka` | `Apache Spark` | 75 | `Kafka` 가 사전에 있는데도 |
| `ML` | `XML` | 80 | 다른 것 |
| `MSSQL` | `MySQL` | 80 | 다른 DB |
| `OpenCL` | `OpenCV` | 83 | 다른 것 |

DevSkill 에서 문제가 안 되는 이유는 입력이 다르기 때문이다. 거기서는 LLM 이
“이건 기술 이름”이라고 판단해 제안한 소수의 이름을 사전에 스냅한다. 우리는 후보가 많고
기술 약어는 짧고 서로 닮아서 문자열 거리를 믿을 수 없다.

그래서 정규화는 **명시적 별칭 조회로만** 한다. 사전에 없는 이름은 억지로 붙이지 않고 그대로 둔다.

## 고칠 일이 생기면

- **같은 기술이 두 이름으로 나온다** → `tech_aliases.json` 에 한 줄
- **기술이 아닌 말이 잡힌다** → `tech_blocklist.txt` 에 한 줄
- **한글 기술어를 놓친다** → `tech_ko_allowlist.txt` 에 한 줄
- **새 기술을 넣고 싶다** → `tech_corpus.json` 에 한 항목 추가 (위 "기술을 하나 더 넣으려면")
