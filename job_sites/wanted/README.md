# Wanted 채용공고 스크래퍼

`.env` 에 적은 조건으로 Wanted 공고를 전량 수집해 `csv/wanted_post.csv` 를 만든다.

```bash
cd job_sites/wanted
python3 wanted.py
```

`requests` `tqdm` `pandas` `python-dotenv` 가 필요하다. 이 기기의 시스템 python3(3.14)과
`analyze-company/.venv` 양쪽에 이미 깔려 있어 그대로 돌아간다. 다른 기기라면
`pip install requests tqdm pandas python-dotenv`.

테스트(네트워크를 타지 않는다):

```bash
python3 tests/run.py
```

## 산출물

`csv/wanted_post.csv` — UTF-8 BOM(엑셀에서 한글이 안 깨진다), 컬럼은 다음 12개.

**덮어쓰지 않고 쌓는다.** 주기로 돌리는 파이프라인이라 매 실행이 파일을 갈아엎으면
마감돼 내려간 공고가 흔적 없이 사라진다. 공고 URL 을 키로 병합하며, 이번에 안 보인 공고도
바로 지우지 않고 `최종확인일` 을 그대로 둔다. **30일 넘게 안 보이면 뺀다.**
자세한 규칙은 `../_common/README.md` 의 "재실행 — 덮어쓰지 않고 쌓는다" 절.

| 컬럼 | 내용 |
|---|---|
| 기업명 | 회사 이름 |
| 마감일 | `2026-09-30`. 마감일이 없으면 `상시채용` |
| 지원자격 | 공고의 '자격요건' 원문 |
| 우대사항 | 공고의 '우대사항' 원문 |
| 경력 | `신입` / `신입~3년` / `3~10년` / `5년 이상` / `경력무관` |
| URL | 공고 주소 |
| 연봉 | **항상 빈칸.** Wanted 는 공고에 연봉을 공개하지 않는다. 다른 사이트 CSV 와 스키마를 맞추려고 칸만 둔다 |
| 기술스택 | 회사가 체크한 태그 + 산문에서 찾은 것, comma 구분. **비면 그 행을 뺀다** |
| 근무지 | `서울 강남구 테헤란로 445, …`. 회사 입력 주소에 구 이름이 없으면 `서울 강남구 · 테헤란로 201` 처럼 앞에 붙인다 |
| 사이트명 | `wanted` 고정 |
| 최초수집일 | 이 공고를 처음 본 날. **오늘 새로 뜬 공고를 여기서 가린다** |
| 최종확인일 | 마지막으로 목록에 있던 날. 오늘이 아니면 **내려간 공고**다 |


실행 락. 자세한 건 `../_common/README.md`.

## .env 작성법

**`.env` 는 저장소에 들어가지 않는다.** 직접 만들어야 실행된다. 예시 파일도 두지 않는다 —
희망 근무지 하나만으로도 어디 사는지 가늠할 수 있고, 앞으로 API 키 같은 것이 들어갈 자리다.
**없으면 안 도는 것이 맞다.**

```bash
# 저장소 루트(analyze-company/)에 .env 를 만든다
touch ../../.env
```

아래 항목을 적는다. `.env` 위치는 이 파일 기준 `../../.env` 다.
**값은 본인 것을 채운다. 이 문서에는 남기지 않는다** — 공개 저장소에 구직 조건이 그대로 남는다.

```bash
JOB_GROUP_IDS=       # 필수. 직군 코드 (아래 "직군 코드" 표)
JOB_IDS=             # 직무 코드. 비우면 직군 전체
EMPLOYMENT_TYPES=    # regular / contract / intern. 비우면 regular,intern
YOE=                 # 신입=0, N년차=N(1~10), 전체=-1. 비우면 -1
HOME_LOCATIONS=      # 희망근무지. 비우면 전국
TECH_STACKS=         # 보유 기술스택. 현재 미적용
HOPE_ANNUAL_SALARY=  # Wanted 는 연봉 미공개라 미적용
```

> 위 블록은 **읽기용 설명이라 주석을 값 옆에 뒀다.** 실제 `.env` 에는 이렇게 쓰지 마라 —
> 값이 비어 있으면 주석이 값으로 읽힌다. 주석은 항목 위에 따로 쓴다.

> **값 뒤에 같은 줄로 주석을 달지 마라.** 값이 비어 있으면 주석이 값으로 읽힌다.
> 주석은 항목 위에 따로 쓴다. (`#` 앞에 공백이 있을 때만 주석이라 `TECH_STACKS=C#` 는 안 잘린다)

| 항목 | 필수 | 뜻 |
|---|---|---|
| `JOB_GROUP_IDS` | O | 직군 코드. comma 구분. 예 `518` |
| `JOB_IDS` | | 직무 코드. comma 구분. **비우면 그 직군 전체** |
| `EMPLOYMENT_TYPES` | | `regular`(정규직) `contract`(계약직) `intern`(인턴). 기본값 `regular,intern` |
| `YOE` | | 경력. 신입=`0`, N년차=`N`(1~10), 전체=`-1`. 기본값 `-1` |
| `HOME_LOCATIONS` | | 희망근무지. 한글 이름 또는 slug. **비우면 전국** |
| `TECH_STACKS` | | **현재 미적용.** 전량 수집 단계라 스택으로 거르지 않는다 |
| `HOPE_ANNUAL_SALARY` | | **적용되지 않는다.** Wanted 가 연봉을 안 주므로 실행 끝에 경고만 뜬다 |

예시 — 개발 직군(`518`)에서 서버 개발자(`872`)·웹 개발자(`873`) 공고를 서울에서.
**본인 조건으로 바꿔 쓴다:**

```bash
# 직군 코드
JOB_GROUP_IDS=518

# 직무 코드
JOB_IDS=872,873

# 고용형태
EMPLOYMENT_TYPES=regular,intern

# 경력
YOE=-1

# 희망근무지
HOME_LOCATIONS=서울

# 아래 둘은 현재 미적용
TECH_STACKS=
HOPE_ANNUAL_SALARY=
```

`JOB_GROUP_IDS` 에 여러 직군을 적으면 직군마다 따로 수집해 합친다 —
Wanted API 가 `job_group_id` 를 하나만 받기 때문이다.

## 기술스택

기술 이름은 **상세 응답 한 벌 안의 두 자리**에서 나온다. API 호출은 한 번뿐이고, 사이트는 보지 않는다.

| | 자리 | 생김새 | 회사가 채우는 법 |
|---|---|---|---|
| ① | `job.skill_tags` | `[{"tag_type_id":1554,"text":"Python"}, …]` | 원티드 목록에서 **골라 체크** |
| ② | `job.detail.requirements` · `preferred_points` · `main_tasks` | `"RDBMS(PostgreSQL 등) 및 NoSQL 설계…"` | **문장으로 씀** |

**둘은 서로를 포함하지 않는다.** 122건 실측:

| | 값 |
|---|---|
| ①을 채운 공고 | 29건 (24%) |
| ①에 적힌 기술 중 ②에도 나오는 것 | 102 / 183 (56%) — **81개는 ①에만** |
| ①이 비고 ②에만 기술이 있는 공고 | 87건 |
| ①②  둘 다 없는 공고 | 4건 → **CSV 에서 제외** |

그래서 **①②를 합쳐서** 넣는다. 회사가 체크한 것을 앞에, 산문에서 찾은 것을 뒤에 놓는다.
둘 다 없는 공고는 판단할 재료가 없어 행에서 뺀다.

### 표기 정규화 — 사이트 공통 계층이 맡는다

합치려면 표기가 같아야 한다. **탐지**와 **정규화**는 역할이 다르고, 사는 곳도 다르다.

| 단계 | 어디 | 무엇 |
|---|---|---|
| 탐지 | `tags/wanted_skill.json` (7,956개) | 산문에서 후보를 찾는 **넓은 그물**. Wanted 고유 |
| 정규화 | `../_common/` (349개) | 찾은 이름을 **한 표준 이름으로** 모은다. 사이트 공통 |

찾는 규칙(단어경계·버전 숫자·짧은 이름·한글)도 사이트 공통이라 `../_common/skills.py` 에 있다.
`lib/skills.py` 가 하는 일은 Wanted 고유한 것 둘뿐이다 — 자기 스킬 사전을 어휘로 넘기는 것과,
① 태그를 `tag_type_id` 로 푸는 것.

공통 계층은 `../_common/README.md` 를 보라. 요지는 셋이다.

- **표준 이름과 분류(`kind`)의 출처** — `_common/tech_corpus.json`. `Apache Kafka`→`Kafka`,
  `GCP`→`Google Cloud`, `Spring Framework`→`Spring`. 나중에 사람인·잡코리아를 붙여도
  같은 기술이 여러 이름으로 갈리지 않는다
- **① 은 문자열이 아니라 `tag_type_id` 로 찾는다** — Wanted 가 준 문자열이 자기 corpus 와
  다를 때가 있다 (실측: `GitHub`/`Github`, `PyTorch`/`Pytorch`). id 로 Wanted 표기를 얻은 뒤
  공통 계층이 표준으로 모은다
- **편집거리 매칭은 쓰지 않는다** — `REST`→`Rust`, `Apache Kafka`→`Apache Spark` 처럼
  다른 기술로 붙는다. 근거는 `_common/README.md`

**한글은 corpus 를 열지 않는다.** Wanted corpus 에 `운영` `감사` `보증` `디자인 관리` 같은
일반명사가 한글 스킬로 들어 있어 산문에 그대로 매칭하면 오탐이 쏟아진다. 그래서 뜻이
하나뿐인 말만 `_common/tech_ko_allowlist.txt` 에 적어 쓴다. 영문은 일반명사와 잘 안 겹쳐서
corpus 전체를 쓴다.

② 매칭 규칙:

- 영문은 단어경계로만 맞춘다. 뒤에 붙는 버전 숫자는 인정한다 (`Python3` → `Python`)
- 1~2글자는 오탐(`IR` `SD` `PC`)이 많아 막고, `C` `R` `Go` `C#` `C++` `JS` `AI` `ML` 만 통과시킨다
- 긴 이름부터 맞춘다 — `Spring Boot` 가 `Spring` 에 먹히지 않게
- 한글은 단어경계가 없어 포함 여부로 찾되, **뒤에 오는 것이 조사·어미·접미사인지**로 낱말 끝을 판정한다 (`컨테이너를` 통과, `컨테이너선` 거부). 근거는 `../_common/README.md` 의 "한글은 낱말 경계가 없다"

**오탐을 보시면** `../_common/tech_blocklist.txt` 에 한 줄 추가하고 다시 돌리면 된다.
블록리스트는 ② 에만 적용된다 — ① 은 회사가 직접 체크한 것이라 그대로 둔다.

`.env` 의 `TECH_STACKS` 는 **현재 적용하지 않는다.** 전량 수집 단계라 스택으로 행을 거르지 않는다.

## 차단 회피

Wanted 앞단의 CloudFront 가 **User-Agent 에 `HeadlessChrome` 이 들어가면 403** 을 준다.
쿠키·토큰·CSRF 는 필요 없고 UA 하나가 게이트다. `lib/client.py` 가 실제 Chrome 과 같은
헤더 묶음(`User-Agent`, `Accept-Language`, `sec-ch-ua`, `sec-fetch-*`, `Referer`)을 보내고,
세션 하나를 재사용하며 요청 사이에 0.2~0.5초 지터를 둔다. 403 을 받으면 그 자리에서 멈추고
UA 를 의심하라고 알려 준다.

**HTML 페이지는 건드리지 않는다.** 필요한 값이 전부 API 에 있고(아래 참조), API 만 쓰는 쪽이
화면 구조 변경에 흔들리지 않는다. 지역 코드표 `tags/wanted_location.json` 은 저장된 정적 파일을 쓴다.

## API

| | |
|---|---|
| 목록 | `GET /api/chaos/navigation/v1/results` — `limit` + `offset`, `links.next` 가 `null` 이면 끝 |
| 상세 | `GET /api/chaos/jobs/v2/{job_id}/details` |
| 필터 어휘 | `tags/wanted_location.json` (정적). 원본은 `/wdlist/{직군}` HTML 의 `__NEXT_DATA__.props.pageProps.filterData` 였다 |

상세 API 의 본문 7개 필드(`position` `intro` `main_tasks` `requirements` `preferred_points`
`benefits` `hire_rounds`)는 공고 페이지가 쓰는 데이터와 20건 전수 대조에서 **바이트 단위로 같았다.**
공고 페이지를 따로 긁을 이유가 없다.

### 페이지네이션

`limit=100` 으로 `offset` 을 100씩 올리며 받는다. 실측으로 확인한 서버 동작:

| 상황 | 서버 응답 |
|---|---|
| 남은 게 `limit` 보다 적다 | 남은 만큼만 준다. `limit` 은 **최대**지 요구 수량이 아니다 |
| 페이지가 정확히 꽉 찼고 남은 게 없다 | `data` 는 꽉 차고 **`links.next` 는 `null`** (전체 49건에 `limit=49` → 49건 + next 없음) |
| 전체가 `limit` 보다 적다 | 한 번에 다 주고 `links.next` 는 `null` |
| offset 이 전체를 넘었다 | 빈 배열 + `links.next` 는 `null` |
| `limit=0` 또는 음수 | HTTP 200 에 **빈 배열** |

`links.next` 가 잔여 여부를 정확히 반영하므로 **`limit` 을 동적으로 줄일 필요가 없다.**
오히려 줄이다 0 에 닿으면 빈 배열을 '끝'으로 오해하게 된다.

진짜 위험은 페이지 크기가 아니라 다른 둘이고, `lib/collect.py` 의 루프가 이를 막는다.

1. **서버가 offset 을 무시하고 같은 페이지를 반복** → 그 페이지에 새 공고번호가 하나도 없으면 중단
2. **수집 중 공고가 추가·삭제돼 경계가 밀림** → 공고번호로 dedupe 해서 중복도 누락도 티가 나게 한다

여기에 폭주 방지용 `offset` 상한(`MAX_OFFSET = 100_000`)을 더했다. 종료 사유는 실행할 때마다
"목록 수집 종료 사유" 로 출력한다 — 왜 멈췄는지가 보이지 않으면 조용한 유실을 알아챌 수 없다.
