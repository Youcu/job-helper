# 결정과 근거

규약이 왜 그 모양인지의 기록이다. **근거는 전부 실측이다** — 짐작으로 정한 것은 없다.
나중에 상황이 바뀌면 여기 숫자를 다시 재서 뒤집으면 된다.

---

## D-01 · 사이트는 API 만 쓴다. HTML 은 안 긁는다

**확인한 것** — 공고 페이지의 `__NEXT_DATA__` 와 상세 API 응답을 20건 전수 대조했다.
본문 7필드(`requirements` `preferred_points` `position` `main_tasks` `intro` `benefits`
`hire_rounds`)가 **바이트 단위로 같았다.** 마감일도 20/20 일치.

오히려 API 에만 있는 필드가 더 많았다(`skill_tags` `attraction_tags` `wanted_pick`).
페이지 데이터에는 `skill_tags` 가 **아예 없다.**

**그래서** — API 만 쓴다. 화면 구조가 바뀌어도 흔들리지 않는다.

**새 사이트에서 할 일** — 같은 대조를 먼저 한다. 다르면 무엇이 부족한지 적고 판단한다.

## D-02 · 페이지네이션에서 `limit` 을 동적으로 줄이지 않는다

**확인한 것** — 전체가 정확히 49건인 조건으로 경계를 찔렀다.

| 요청 | 받은 건수 | `links.next` |
|---|---|---|
| `limit=25 offset=25` | 24 | 없음 |
| `limit=49 offset=0` | 49 | **없음** |
| `limit=50 offset=0` | 49 | 없음 |
| `limit=0` / `-1` | 0 | 없음 (HTTP 200) |

`limit` 은 **최대**지 요구 수량이 아니다. 페이지가 딱 꽉 차도 남은 게 없으면 `next` 가 없다.

**그래서** — 줄일 이유가 없다. 오히려 **`limit=0` 이 200 에 빈 배열을 주므로**, 줄이다 0 에
닿으면 "끝" 으로 오해한다.

**대신 막은 것** — 서버가 offset 을 무시해 같은 페이지를 반복하는 경우, 수집 중 공고가
추가·삭제돼 경계가 밀리는 경우, 폭주. 그리고 **종료 사유를 출력**한다.

## D-03 · 기술 이름은 응답의 두 자리에서 모두 뽑아 합친다

**확인한 것** — 기술 이름은 상세 응답 한 벌 안의 두 자리에서 나온다.
① `skill_tags`(회사가 목록에서 골라 체크) ② 산문(`requirements` 등).

122건 실측:

| | |
|---|---|
| ① 을 채운 공고 | 29 / 122 (24%) |
| ① 의 기술 중 ② 에도 나오는 것 | 102 / 183 (56%) |
| **① 에만 있는 기술** | 81개 |
| **① 이 비고 ② 에만 있는 공고** | 87건 |

**어느 한쪽도 다른 쪽을 포함하지 않는다.**

**그래서** — 합친다. 회사가 체크한 것을 앞에, 산문에서 찾은 것을 뒤에.
①②  둘 다 없으면 판단 재료가 없으므로 행을 뺀다.

## D-04 · 표기 정규화는 편집거리로 하지 않는다

**확인한 것** — Reference Project Repo 인 DevSkill 의 `canonicalize()`(rapidfuzz,
threshold 70~85)를 우리 174종에 걸었다.

| 입력 | fuzzy 결과 | 점수 | 등장 |
|---|---|---|---|
| `REST` | **`Rust`** | 75 | 17회 |
| `Apache Kafka` | **`Apache Spark`** | 75 | 10회 |
| `ML` | **`XML`** | 80 | 12회 |
| `MSSQL` | **`MySQL`** | 80 | 3회 |

`Kafka` 가 사전에 있는데도 `Spark` 로 갔다. threshold 85 로 올리면 오매칭은 사라지지만
붙는 것도 2종뿐이다.

**왜 거기서는 되나** — DevSkill 은 **LLM 이 "이건 기술 이름" 이라고 판단해 제안한 소수의
이름**을 스냅한다. 우리는 후보가 많고 기술 약어는 짧고 서로 닮았다.
**같은 함수라도 입력이 다르면 결과가 다르다.**

**그래서** — 명시적 별칭 조회만 쓴다. 사전에 없는 이름은 억지로 붙이지 않고 그대로 둔다.

## D-05 · 공통 corpus 는 씨앗을 병합한 것이지, 갈아탄 것이 아니다

**확인한 것** — DevSkill 온톨로지 271개는 우리가 뽑은 이름의 **등장 기준 67%** 만 덮었다.
못 덮는 것에 `GitHub` `Spring` `REST API` `Google Cloud` `NestJS` `Grafana` `RDBMS` 가 있었다.

**그래서** — 씨앗으로 쓰고 공고 실측 78개를 더해 **349개**로 만들었다.
`kind` 는 DevSkill 의 6종에 `concept`(OOP·TDD·마이크로서비스)과
`protocol`(TCP·HTTP·OAuth)을 더했다 — 채용공고에는 제품이 아닌 것도 기술 요구로 적힌다.

씨앗은 이미 `tech_corpus.json` 안에 합쳐져 있다. **재생성 스크립트는 지웠다** —
개인 절대경로가 박혀 있고 데이터가 이중으로 존재했다. 새 기술은 그 JSON 에 한 항목 더한다.

## D-06 · 한글 낱말 경계는 목록이 아니라 규칙으로 판정한다

**문제** — 한글은 단어경계가 없다. `가상화폐` 안에 `가상화` 가, `컨테이너선` 안에
`컨테이너` 가 들어 있다.

**처음 한 것** — 충돌 복합어를 파일에 적어 막았다. **잘못된 설계였다.**

**확인한 것** — 공고 600건(62만 자)에서:

| | 매치 |
|---|---|
| 아무 판정 없이 | 394회 |
| **제외어 목록** | **394회 — 0건 걸러냄** |
| 조사 규칙 | 394회 |

적어 둔 네 낱말이 그 표본에 **한 번도 안 나왔다.** 117건에서 한 번 본 걸로 만든 목록이었다.

**그래서** — 조사·어미·접미사라는 **닫힌 문법 부류**로 판정한다. 한국어 문법이 정했고
새 기술이 나와도 안 늘어난다.

```
컨테이너를  → 를은 조사   → 통과      컨테이너선 → 선은 셋 다 아님 → 거부
분산 처리한 → 한은 어미   → 통과      가상화폐   → 폐는 셋 다 아님 → 거부
컨테이너화  → 화는 접미사 → 통과
```

형태소 분석기(kiwipiepy)도 재 봤다. 정확도 같고(393회) 공고당 3.2ms 와 C++ 확장 의존성이
늘어 쓰지 않았다.

**일반 원칙** — [04-code-conventions.md](04-code-conventions.md) 의 "목록 vs 규칙".
못 덮는 것이 생겼을 때 **틀린 값이 들어가면 규칙**, **빠지기만 하면 목록**도 된다.

## D-07 · 덮어쓰지 않고 쌓는다. 30일 보존

**확인한 것** — 몇 시간 사이 수집 대상이 122 → 121건이 됐다. 확인해 보니 한 건이
`status=close` 로 마감돼 내려간 것이었다. 덮어쓰기였다면 지원을 준비하던 공고가
흔적 없이 사라진다.

**그래서** — 공고 URL 을 키로 병합한다. 이번에 안 보인 공고도 남기되 **30일 넘으면 뺀다.**
영영 쌓으면 지원할 수도 없는 공고가 지금 열린 것과 섞인다.

**따라온 것** — 쌓는 구조가 되면 파일 하나에 이력이 전부 들어간다. 한 번 깨지면 못 되돌린다.
그래서 **원자적 쓰기**와 **실행 락**을 함께 넣었다.

## D-08 · 설정은 `.env` 파일만 읽는다

**확인한 것** — `load_dotenv()` 는 값을 `os.environ` 에 심는다. `.env` 에 줄이 없는 항목은
셸 환경변수에서 새어 든다. 근무지를 안 적었는데 셸에 `HOME_LOCATIONS=부산` 이 있으면
**부산 공고를 긁는다.**

**그래서** — `dotenv_values()` 로 파일만 읽는다.
조건이 파일에 안 적힌 채 결과가 달라지면 **재현이 안 된다.**

## D-09 · 실행 주기는 이 저장소가 정하지 않는다

스크래퍼는 추후 만들 **오케스트레이터 안의 단일 작업**이다. 언제 얼마나 자주 도는지는
그쪽이 정한다.

**여기서 지는 책임은 "몇 번을 돌려도 안전하게" 까지다** — 누적 병합, 30일 보존,
원자적 쓰기, 실행 락.

다만 알아 둘 것: 테스트는 떠 놓은 응답을 쓰므로 사이트가 API 를 바꿔도 통과한다.
**정기 실행이 사실상 유일한 감시 수단**이고, 신호는 실행 시 뜨는 실패 건수와 CSV 빈 칸이다.

## D-10 · 사이트에 없는 데이터는 칸을 비우고 사실을 알린다

**확인한 것** — Wanted 상세 응답 60건 전문에서 `salary|annual_income|pay|compensation|wage`
를 검색했다. **0건.** 필드 자체가 없다.

**그래서** — `연봉` 컬럼을 빼지 않고 빈 문자열을 넣는다. CSV 를 합칠 때 모양이 어긋나면
안 된다. `.env` 의 `HOPE_ANNUAL_SALARY` 도 적용하지 않고, 실행이 끝날 때 그 사실을 알린다.

## D-11 · `.env` 는 저장소에 넣지 않고 예시 파일도 두지 않는다

**왜** — 민감 정보를 막으려고 있는 파일이다. 희망 근무지 하나만으로도 어디 사는지 가늠할 수
있고, 앞으로 API 키 같은 것이 들어갈 자리다.

**예시 파일을 안 두는 이유** — `.env.example` 을 만들면 항목을 채워 넣다가 실제 값이 따라
들어간다. 실제로 그렇게 만들었다가 근무지가 그대로 들어갔다.

**그래서** — 없으면 안 도는 것이 맞다. 필요한 항목은 사이트 `README.md` 에 적고,
클론한 사람이 직접 만든다.

## D-12 · 산출물과 중간 문서는 추적하지 않는다

| | 왜 |
|---|---|
| `<사이트>/csv/` | **사람마다 스크랩 대상이 다르다.** 남의 조건으로 뽑은 CSV 를 받을 이유가 없다 |
| `<사이트>/docs/` | 그 단계를 **만들어 가는 중간 확인용**이다. 보는 대상이 만드는 사람과 에이전트라, 완제품을 쓰는 사람에게는 쓸모가 없다 |

루트 `docs/` 는 추적한다 — 규약은 쓰는 사람에게도 필요하다.

## D-13 · 그림 본문은 수집 단계에서 읽지 않는다. 주소만 남긴다

**확인한 것** — 사람인 380건 중 **84건(22%)이 본문이 그림 한 장**이다. 그림을 읽는 데
장당 40초라 수집이 **4시간**이 됐다. 파이프라인은 주기로 도는데 쓸 수 없는 시간이다.

| | 판독을 수집에 넣었을 때 | 주소만 남겼을 때 |
|---|---|---|
| 380건 수집 | 31분 | **8분 33초** |
| 건당 | 5초 | 1.3초 |
| 외부 호출 | 40회 | **0회** |
| 기술 없어 제외된 공고 | 43건 | 23건 |

**그래서** — 수집은 **순수 HTTP** 만 한다. 본문이 그림이면 `기술스택` 칸에 **그림 주소를
남긴다.** `http` 로 시작하니 기술 이름과 섞이지 않고, 나중 단계가 그걸로 대상을 고른다.

**스키마를 안 늘린다.** 12칸은 사이트가 공유한다. "그림이 남았나" 칸을 더하면 그 칸을
안 쓰는 사이트에도 빈 칸이 생기고 합칠 때 어긋난다.

**읽는 것은 수집이 끝난 뒤 도는 별도 단계다.** 합본(`csv/merged.csv`)을 읽어
`csv/merged_read.csv` 를 낸다. 원본을 그대로 두므로 두 파일을 견주면 무엇이 채워지고
무엇이 버려졌는지 전부 보인다 — 따로 사본을 두지 않는 이유다.

**되돌릴 조건** — 그림 본문 비율이 5% 아래로 떨어지면 별도 단계를 둘 값이 없다.

## D-14 · corpus 는 사람이 승인해야 늘어난다

**왜** — `tech_corpus.json` 은 사이트 공통 표준이고, 거기 있는 이름은 `build_matcher()` 를
통해 **모든 사이트의 산문 매칭 어휘가 된다.** 잘못 읽은 이름이 자동으로 들어가면

1. 다른 사이트 본문에서도 매칭되기 시작하고
2. 매칭돼서 CSV 에 나오니 멀쩡해 보이고 (**자기 강화**)
3. 누적 CSV 에 퍼진 뒤에는 되돌리기 어렵다

D-04(편집거리 금지)와 D-06(한글 경계)에서 정한 방향과 같다 — *놓치면 틀린 데이터가
들어오고 과하면 데이터가 없어진다. 없어지는 편이 낫다.*

**그래서** — 자동 반영 후 사후 검토가 아니라, **후보로 쌓고 사람이 옮긴다.**

### 무엇이 corpus 에 들어갈 자격이 있는가

**개념이냐 아니냐가 아니라, 변별력이 있느냐로 가른다.**

처음에는 "개념이면 뺀다" 로 갈랐다가 틀렸다는 것을 알았다. 개념이라서 빼는 게 아니라
**모두가 갖다 붙일 수 있어서** 빼는 것이다.

> 물어볼 것 하나 — **"이걸 다룰 줄 아느냐"에 사람마다 답이 갈리는가.**

| | 예 | 판단 |
|---|---|---|
| 답이 갈린다 | `Transformer` `CNN` `RAG` `LoRA` | **남긴다.** 형태가 개념이어도 구현에 실력 차가 난다. AI 쪽에서는 이런 것을 *구체적으로 다룰 수 있느냐* 를 묻는다 |
| 답이 안 갈린다 | `CI/CD` `MSA` `AI/ML` | 뺀다. 안 한다고 말하는 회사가 없다 |
| | `GitHub` `Slack` `JIRA` | 뺀다. 계정만 있으면 된다 |
| | `MCP` `JSON` | 뺀다. 개나 소나 쓴다 |

`Transformer` 는 남고 `CI/CD` 는 빠진다 — 둘 다 형태는 개념이다.
가르는 것은 **깊이**다. 익히는 데 시간이 드는가, 잘하고 못하고가 있는가.

뺀 이름은 `_common/tech_rejected.txt` 에 둔다. 그래야 다음 실행에서 다시 후보로
올라오지 않고, 진짜 후보가 그 속에 묻히지 않는다.

**다만 버려진 이름은 CSV 에 흔적이 없다.** 후보 파일이 없으면 아무도 모르게 사라진다.
그래서 `corpus_candidates.json` 은 편의 기능이 아니라 **누락을 복구 가능하게 만드는 장치**다.
관측 횟수·사이트·예시 URL·닮은 표준 이름을 함께 남겨 판단을 2분짜리로 만든다.
`닮은 표준 이름` 은 제안이 아니라 **경고**다 — `REST`/`Rust` 를 눈에 걸리게 하려는 것이다.

## D-15 · 직무는 사이트 코드가 아니라 **이름**으로 적는다

**왜** — 처음에는 사이트마다 코드를 따로 적게 했다. `WANTED_JOB_IDS=872`,
`SARAMIN_JOB_IDS=84`, `JOBKOREA_JOB_IDS=1000229` … 코드 체계가 사이트마다 다르니
어쩔 수 없다고 봤다. 여섯이 되자 **사람이 여섯 벌을 맞춰 적는 쪽이 더 위험했다.**
하나를 빠뜨리면 그 사이트가 남의 코드를 받아 엉뚱한 것을 긁는데 **예외도 안 나고
결과도 나온다.** 실제로 그렇게 만들었다가 고쳤다.

**그래서** — `.env` 에는 `JOB_ROLES=백엔드,웹` 처럼 **여섯이 함께 쓰는 이름**만 적고,
각 사이트가 `tags/<사이트>_role_map.json` 으로 자기 코드를 찾는다.

| | |
|---|---|
| 표준 이름 | `_common/roles.json` — 16개. 별칭도 받는다(`서버`·`Backend` → `백엔드`) |
| 대응 | 각 사이트 `tags/` 에 둔다. **`_common` 은 사이트 코드를 모른다** |
| 1:N | 한 이름이 코드 여럿이 된다 — Wanted 의 `백엔드` 는 넷(`872` `660` `899` `895`) |
| 모르는 이름 | `RoleError` 로 **멈춘다**. 조용히 빼면 조건이 통째로 사라진다 |
| 사이트에 없는 직무 | 화면에 **못 걸었다고 찍는다**. 조용히 빠지면 왜 적은지 못 찾는다 |

이름은 코드가 갖던 함정이 없다 — `백엔드` 는 어느 사이트에서도 `백엔드` 다.

## D-16 · 대응표에는 **이름이 그 역할을 명시하는 코드만** 넣는다

|---|---|
| 제목에 백엔드 낱말 | **3%** |
| 제목에 임베디드 낱말 | **27%** |

**그래서** — `900` 은 백엔드에서 빼고 임베디드로 옮겼다. 같은 기준으로 여섯을 더 뺐다

한 코드가 여러 역할에 걸리는 것은 **사이트가 안 쪼갠 것**이라 우리가 못 나눈다 —
사람인·잡코리아의 `앱개발` 은 안드로이드와 iOS 를 겸한다. 그건 그대로 둔다.

## D-18 · 걷은 것이 없는데 **잃은 것이 있으면** 실패다

**확인한 것** — Pathsdog 의 상세 도구가 죽어 29건이 전부 `internal_error` 를 냈다.
(그 사이트는 계속 불안정해 **뒤에 대상에서 뺐다 — D-24.** 이 규칙은 다른 사이트에도
그대로 필요하므로 남는다.)
공고 하나의 실패를 견디려고 세고 넘어가게 해 뒀는데, **전부 실패해도 똑같이 넘어가
종료 코드 0** 을 냈다. 화면에는 `정상 · 0행` 이라고 찍혔다 — 사이트에 공고가 29건 있는데도.

**그래서** — `_common/outcome.py` 에서 한 줄로 판정한다.

> 저장한 행이 없는데 상세 실패가 하나라도 있었다 → **종료 코드 2**

`0행` 자체는 정상일 수 있다. 공고가 없거나, 받아서 다 걸러졌을 수 있다. **그 둘과 "못 받은
것" 을 가르는 것**이 이 판정이다 — 남은 것이 없는데 잃은 것이 있으면 이 실행만 보고는
*사이트에 공고가 없는 건지 우리가 못 받은 건지* 알 수 없다. 알 수 없는 것을 `정상` 이라고
말하면 안 된다.

**비율로 자르지 않는다.** 처음에는 "전부 실패" 로 잡았는데, 상세 하나만 성공하고 그것마저
근무지 조건에 걸려 빠지자 0행인데 종료 코드 0 이 나왔다 — 실제 실행에서 그렇게 한 번
새어 나갔다. 저장한 행으로 판정하니 그 경우도 잡힌다. 절반·80% 같은 선은 근거가 없어
두지 않는다. **하나라도 건졌으면** 그 실행은 무언가를 해냈고, 잃은 건수는 요약에 찍힌다.

## D-19 · 그림은 **여백에서 잘라** 넣는다. 통째로 넣지 않는다

**확인한 것** — 같은 그림(1505×21708)·같은 모델(sonnet)로.

| | 기술스택 | 자격요건 | 우대사항 | 시간 |
|---|---|---|---|---|
| 통째로 | 24개 | **0개** | **0개** | 32.7초 |
| 7조각 | 18개 | **5개** | **6개** | 23.1초 |

시간은 참고만 한다 — 통째로 쪽은 `--max-turns 4` 로 프롬프트도 조금 달리해서 잰 값이라
조각 쪽과 조건이 안 맞는다. **이 표의 요점은 초가 아니라 칸 수다.**

그림에는 자격요건 5개와 우대사항 6개가 또렷이 있다. 눈으로 확인했다. 통째로 넣으면 긴 변에
맞춰 축소돼 작은 글씨가 뭉갠다.

**그래서** — 세로가 가로의 2.4배를 넘으면 **여백에서** 자른다. 등분은 글줄을 자르므로,
가로 한 줄이 통째로 무늬 없는 곳을 찾아 그 한가운데를 자른다. 실측한 그림에 20px 이상
여백 띠가 126개, 띠 없는 최장 구간이 1,794px 로 목표 높이보다 짧아 늘 찾았다(강제 0건).

**모델을 바꿔 풀 문제가 아니다.** 축소된 픽셀에 글자가 없으면 opus 도 못 읽는다. 같은 조각
입력으로 재 보니 opus 와 sonnet 의 결과가 글자까지 같고 비용은 2.5배였다 — sonnet 을 쓴다.

**되돌릴 조건** — 어려운 그림(저해상도·손글씨풍·복잡한 표)에서 sonnet 이 눈에 띄게 놓치면
`IMAGE_MODEL` 로 바꿔 재 보고, 그 측정으로 기본값을 옮긴다.

## D-20 · 판독 캐시의 열쇠는 **공고의 주소 목록 전체**다. 낱장 주소가 아니다

**확인한 것** — 실제로 걷은 `merged.csv` 의 그림 주소 33개를 훑었다.

| 주소 | 쓰는 공고 |
|---|---|
| `…/hiring/images/blank.png` | **서로 다른 두 회사** |
| `…/images/template/toptype/it1.webp` | 사람인 공용 템플릿 — 성격상 여럿 |

한 공고의 그림들은 **합쳐서 한 번** 읽으므로 그 답은 그 조합의 답이다. 그런데 낱장 주소
마다 그 답을 넣어 두면, 같은 그림을 쓰는 다른 공고가 캐시 적중으로 **남의 자격요건을 자기
것으로 받아 간다.** 이름은 B 회사인데 내용은 A 회사인 행이, 버려지지도 않고 캐시 파일에
남는다 — 눈에 안 띄는 채로.

**그래서** — 열쇠는 주소들을 **차례까지 지켜 공백 하나로 이어 붙인 것**이다. 주소에는
공백이 못 들어가므로(RFC 3986) 경계가 헷갈리지 않고, 해시와 달리 캐시 파일을 열어 보면
어느 공고의 답인지 눈으로 알아본다. **공고 하나에 열쇠 하나, 답 하나.**

덤으로, 그림 여러 장 중 한 장만 캐시에 없다고 전부 다시 받아 읽던 낭비도 사라진다.

**옛 캐시의 낱장 열쇠는 전부 빗나간다.** 한 번 다시 읽으면 그만이다 — 캐시는 편의지
진실이 아니고, **잘못 맞는 것보다 안 맞는 것이 낫다.**

## D-21 · **"못 열었다" 는 버림이 아니다.** 껍데기와 우리 쪽 실패를 가른다

**확인한 것** — `is_junk` 가 `Image.open` 의 예외를 전부 "껍데기" 로 삼키고 있었다. 그러면
그 공고는 버려지고 **빈 결과가 캐시에 남아 다음 실행에도 다시 시도하지 않는다.** 실제로
걸릴 길이 둘 있다 — 만료된 공고가 200 으로 주는 안내 페이지 HTML, 그리고 Pillow 가 기본
플러그인으로 못 여는 AVIF·HEIC.

**그래서** — `is_junk` 는 **크기만** 판정한다(가로·세로 100px 미만). 못 여는 것은 내려받기
실패와 같은 `FetchError` 로 올려 그 행을 원래 모습대로 남기고 캐시에 넣지 않는다.
`image_process/README.md` 의 "버림과 실패를 가른다" 표가 처음부터 그렇게 적혀 있었다 —
코드가 문서를 어겼던 것이다.

같은 갈래의 결정 하나 더 — **종료 코드 `2` 는 "아무것도 못 해냈다" 일 때만 낸다.** 캐시
적중을 "해낸 것" 에서 빼고 세면, 자리 잡힌 뒤(거의 전부 캐시 적중)에는 **새 공고 하나가
시간 초과만 나도 실행 전체가 실패**로 보고된다. D-18 과 같은 정신이다 — 하나라도 건졌으면
그 실행은 무언가를 해냈고, 잃은 건수는 요약에 찍힌다.

## D-22 · 표본을 거른 조건으로 그 표본을 검사하지 않는다

**무슨 일이 있었나** — 이미지 판독 단계를 설계하며 "그림 주소와 진짜 기술이 한 칸에 섞인
행이 있는가" 를 쟀고, **0건**이라는 답을 얻어 스펙·계획·코드에 박았다. 검사는 이랬다.

```python
img   = [r for r in rows if r["기술스택"].startswith("http")]   # ← 여기서 이미 걸렀다
mixed = [r for r in img if any(not p.startswith("http") for p in parts(r))]
```

**`http` 로 시작하는 행만 골라 놓고 그 안에서 섞인 것을 찾았다.** 기술이 먼저 오는 행은
표본에 애초에 안 들어갔으므로 0 이 나올 수밖에 없었다. 순환 논증이다.

**대가** — 그 0건을 근거로 대상 판정을 `startswith("http")` 로 만들었다. 사람인은 기술을
먼저 주고 주소를 뒤에 붙이는데(`C++, C, Java, https://…png`), 실제 데이터에서 주소가 든
**175행 중 73행(42%)** 이 그 모양이었다. 그 공고들은 판독 단계를 통째로 지나갔고, 내용은
그림 안에 있는데 아무도 안 읽었으며, 주소는 `기술스택` 칸에 남아 다음 단계가 기술 이름으로
읽을 참이었다. 설계할 때 쟀던 데이터에도 이미 24건이 있었다 — 못 본 것뿐이다.

**그래서** — 어떤 성질의 유무를 잴 때, **그 성질로 표본을 거른 뒤에 재지 않는다.** 전수를
훑거나, 거르는 조건과 재는 조건이 독립인지 먼저 확인한다.

이 저장소의 다른 실측들도 같은 눈으로 다시 볼 값이 있다. "N건 중 M건" 형태의 숫자는
**N 을 어떻게 골랐는지**가 답을 정한다.

**되돌릴 조건** — 없다. 이건 방법의 문제라 뒤집을 것이 아니다.

## D-23 · 공고명은 **상세를 먼저** 쓰고, 목록으로 물러선다

**왜 넣었나** — 열두 칸에는 회사와 본문은 있는데 **그 공고가 무엇을 뽑는 자리인지**가
없었다. `기업명 + 지원자격` 만으로는 같은 회사가 올린 서로 다른 공고를 사람이 못 가린다.
실제로 한 회사가 같은 날 두 건을 올린 경우가 이번 수집에도 있다(㈜고워드 2건).

**출처는 사이트마다 다르다. 전부 실제 응답을 찔러 확인했다.**

| 사이트 | 어디서 | 물러설 곳 |
|---|---|---|
| wanted | 상세 `detail.position` | 없다 — 목록 응답에 제목이 아예 없다 |
| saramin | 목록 카드 `div.job_tit > span` | 없다 |
| jobkorea | 상세 JSON-LD `JobPosting.title` | 목록 카드 제목 |
| jobplanet | 상세 `title` | 목록 항목 `title` |
| jumpit | 상세 `title` | 목록 항목 `title` |
| pathsdog | 상세 머리줄 `📋 회사 - 공고명` | 목록에서 가른 제목 |

> 이 표와 아래 실측은 **Pathsdog 를 빼기 전**의 것이다 (D-24). 지운 사이트의 줄은 그때
> 무엇을 쟀는지 남기려고 그대로 둔다.

**상세를 먼저 쓰는 이유** — 목록 카드의 제목은 자리에 맞춰 **말줄임이 붙어 오는 일이
있다.** 상세의 구조화 데이터에는 전문이 있다. `기업명` 을 정하는 규칙과 같은 순서라
사이트마다 다른 규칙을 외울 필요도 없다.

**사람인만 반대인 이유** — 상세에는 같은 글이 제목·탭·`og:title` 로 여러 자리에 흩어져
있어 무엇이 공고 제목인지 가릴 수 없다. 카드는 `div.job_tit > span` 한 자리라 확실하다.
**그리고 이 값은 이미 뽑아 두고 CSV 로만 안 내보내고 있었다.**

**실측** — 2026-09-09 전량 수집. **이번 실행에서 걷은 745행 전부(100%)** 공고명이 찼다.

```
wanted 118  saramin 437  jobkorea 161  jobplanet 6  jumpit 7  pathsdog 16
```

`csv/merged.csv` 763행 중 18행이 비어 있는데, **전부 이번에 안 보인 옛 행**이다 —
칸이 없던 시절에 쌓인 것이라 값이 있을 수 없다. 다시 보이면 채워지고, 30일이 지나면 빠진다.
없는 칸을 빈 문자열로 읽는 `store.read_csv` 덕에 옛 파일도 그대로 읽힌다.

**시험에서 배운 것** — 칸을 늘렸을 때 **구조 검사(`list(row) == COLUMNS`)는 값이 늘 비어
있어도 통과한다.** 실제로 컬럼만 추가하고 여섯 사이트 중 아무 데도 안 채운 상태에서
931건이 전부 초록이었다. 그래서 사이트마다 **실제 응답으로 그 칸이 차는지** 보는 시험을
따로 두고, 여섯 곳 전부 일부러 빈칸으로 되돌려 시험이 잡아내는지 확인했다.
**칸을 늘리는 변경에는 이 확인을 반드시 한다.**

**되돌릴 조건** — 어느 사이트가 제목을 말줄임해서만 준다는 것이 확인되면, 그 사이트에
한해 물러설 순서를 뒤집는다. 지금은 여섯 곳 다 전문이 온다.

## D-24 · Pathsdog 는 대상에서 뺀다. 코드도 지운다

**무슨 일이 있었나** — 여섯 사이트 중 이 한 곳만 실패가 반복됐다. 이 저장소에 남은 기록만
모아도 이렇다.

| 언제 | 무슨 일 |
|---|---|
| D-18 을 만들게 한 실행 | 상세 도구가 죽어 **29건이 전부 `internal_error`**. 목록은 멀쩡히 받았다 |
| 그 뒤 실행 | `0행` 에 종료 코드가 `2`(온전히 못 걷음)로 여러 번 |
| 2026-09-09 | 정상. **16행** — 다섯 사이트 745행 중 2% |

사용자가 사이트를 직접 열어 보고 스크래퍼도 여러 번 돌린 뒤 판단했다: *"애초에 서버 자체가
문제가 있는 경우가 많은 것 같다."* 우리 쪽 코드 문제가 아니다 — 목록은 받아 오는데 상세
도구가 서버에서 죽는다. 재시도로 못 잡는 종류다.

**그래서** — `job_crawling_ochestrator.py` 의 `SITES` 에서 빼고, `job_sites/pathsdog/` 를
통째로 지웠다. 24개 파일 · 1,098줄 · 시험 111건.

**끄지 않고 지운 이유** — 안 도는 코드는 썩는다. 스키마가 바뀌어도(이번 `공고명` 처럼)
안 도는 사이트는 아무도 안 고치고, 시험만 통과한 채 실제로는 못 쓰는 상태로 남는다.
되살릴 일이 생기면 git 이력에 그대로 있다.

**이야기는 남긴다** — `_common/outcome.py` 와 D-18 에 이 사이트 이름이 그대로 있다.
**규칙이 왜 있는지의 근거**라서다. 어느 사이트든 같은 일이 날 수 있고, 그때 그 판정이 잡는다.
근거를 지우면 다음 사람이 규칙을 "쓸데없이 까다롭다" 고 보고 푼다.

**지운 뒤 남는 것** — `csv/merged.csv` 는 매 실행 사이트 CSV 를 다시 이어 붙여 만들므로,
다음 실행에서 Pathsdog 행은 저절로 사라진다. 30일 보존은 **사이트별 CSV 안에서만** 도는
규칙이라 여기엔 걸리지 않는다.

**되돌릴 조건** — 서버가 안정된 것을 **실측으로** 확인하면 되살린다. 되살릴 때는
`docs/convention/03-adding-a-site.md` 의 체크리스트를 처음부터 다시 밟는다 — 그 사이 스키마가
`공고명` 만큼 늘었고, 이력에서 되살린 코드는 그것을 모른다.

## D-25 · 같은 뜻의 말은 **저장할 때 한 곳에서** 한 벌로 맞춘다

**확인한 것** — 전량 지우고 다시 걷은 735행(2026-09-09)을 전수로 보니, 뜻이 같은데
표기만 다른 값이 세 칸에 있었다.

| 칸 | 쪼개진 모습 | 건수 |
|---|---|---|
| 경력 | 사람인 `신입 · 경력` 188 · 잡코리아 `신입·경력` 123 | **311** |
| 마감일 | `상시채용` 104 · 사람인 `채용시` 39 | **39** |
| 근무지 | `서울` 539 · `서울특별시` 27 · `서울시` 17 · `서울전체,` 4 | **54** |

가운뎃점 띄어쓰기 하나로 311건이 두 값으로 갈렸다. **합쳐 놓고 경력으로 거르거나 묶을
수가 없다** — CSV 를 한 벌로 합치는 이유가 바로 그건데.

**원인은 셋 다 같다** — 각 사이트가 **사이트 문구를 그대로 통과시켰다.** 각 사이트 코드에
"없는 날짜를 지어내지 않는다"(`saramin/lib/record.py:95`) 같은 판단이 옳게 적혀 있다.
빠진 것은 그 뒤에 **계약의 말로 옮기는 단계**다.

**그래서** — `store.write_csv()` 가 쓰기 직전에 `to_contract()` 로 맞춘다.
규칙은 `_common/career.py` · `deadline.py` · `place.py` 에 있다.

**왜 사이트마다가 아니라 한 곳인가** — 스키마의 단일 출처가 `store.py` 다. 다섯 곳에
흩어 두면 새 사이트가 붙을 때 한 곳만 빠뜨려도 조용히 어긋나고, 그 어긋남은 합본을 볼
때까지 안 보인다. 사이트의 `to_row()` 는 **그 사이트가 한 말을 그대로** 두는 편이
디버깅에도 낫다 — 무엇이 왔는지와 무엇으로 옮겼는지가 갈린다.

**목록이 아니라 규칙으로 옮긴다** (D-06 과 같다). 사이트 문구를 적어 두고 맞추면 다음
문구에서 뚫린다. 글에서 뜻을 읽는다 — 신입과 경력을 나란히 받는다고 하면 `경력무관`,
숫자가 있으면 범위로.

**시도 17개만 목록이다.** 행정구역이라 관측으로 늘어나지 않는 닫힌 집합이다
(`saramin` 의 고용형태 12개와 같은 이유).

**모르는 글은 지어내지 않는다.** 마감일이 날짜로도 "없다" 로도 안 읽히면 **그대로 남긴다** —
`09-14`(사람인이 연도를 모를 때 주는 값)를 `상시채용` 으로 바꾸면 진짜 마감일을 지운다.
근무지도 시도가 아예 없으면 붙이지 않는다. 다만 **원티드는 등록된 시도가 응답에 있으므로**
그때는 붙인다(`서초구 강남대로 465` → `서울 서초구 …`, 실측 8행).

**옮긴 뒤 실측** — 경력은 15개 값 전부 계약 어휘, 마감일의 비날짜 값은 `상시채용`
하나(143건), 근무지 첫머리는 `서울` 588 · `경기` 127 로 모였다.

**잃는 것** — `경력` 만 적힌 공고(연차를 안 밝힌 경력직)도 `경력무관` 이 된다. 계약에
그 슬롯이 없고, "따지지 않는다" 가 모르는 것을 담기에 가장 덜 틀린 값이다. 실측 데이터에는
0건이라 지금은 영향이 없다. 연차 조건을 넓혀 걷을 때 다시 봐야 한다.

**되돌릴 조건** — 계약이 `신입·경력` 을 독립된 값으로 인정하기로 하면 그때 `career.py` 의
그 갈래만 뺀다. 다만 **두 사이트의 표기를 하나로 맞추는 일은 그래도 남는다.**
