# 테스트 규약

## 목적

**통과시키려고 쓰는 게 아니라 결함을 찾으려고 쓴다.**

이 규칙이 필요한 이유는 분명하다 — 테스트를 나중에 쓰면 이미 있는 동작을 그대로 옮겨
적게 되고, 그러면 전부 통과하지만 아무것도 못 잡는다.

실제로 이 저장소에서는 **처음 돌렸을 때 9건이 실패했고 전부 진짜 결함이었다.**
그중 셋은 조용히 틀린 결과를 내보내고 있었다.

## 쓰는 순서

1. **코드를 적대적으로 읽는다.** "여기가 틀렸을 것 같다" 는 곳을 찾는다
2. **직접 찔러 본다.** 짐작으로 테스트를 쓰지 말고 실제로 값을 넣어 본다
3. **실제로 틀린 것만 테스트로 굳힌다**
4. 코드를 고친다
5. 실패했던 테스트에 **`# 결함:` 주석**으로 무엇이 문제였는지 적는다

```python
def test_EXCEPTION_env_value_containing_hash_is_not_truncated():
    """결함: `#` 을 무조건 주석으로 봐서 `TECH_STACKS=C#,Java` 가 `['C']` 가 됐다.

    C# · F# 은 흔한 스택이다. 값 하나가 아니라 뒤의 목록 전체가 사라졌다.
    """
```

코드를 되돌리면 그 테스트가 먼저 깨진다. 그게 테스트가 하는 일이다.

## 세 갈래

이름 앞자리로 가른다. `tests/run.py` 가 갈래별로 센다.

| 갈래 | 무엇을 보나 |
|---|---|
| `test_NORMAL_…` | 제대로 된 입력이 제대로 나오는가 |
| `test_EXCEPTION_…` | 망가진 입력에 어떻게 반응하는가 |
| `test_BOUNDARY_…` | 0, 1, 최대, 딱 떨어지는 지점, 뒤집힌 범위 |

**예외와 경계가 일반보다 많아야 한다.** 지금 비율은 일반 19 · 예외 34 · 경계 35 다 (합 88건).
일반 케이스는 대개 저절로 맞는다. 틀리는 곳은 나머지 둘이다.

### 예외에서 꼭 보는 것

- 설정 파일: 없음 · 빈 값 · 타입 틀림 · 범위 밖 · 값에 특수문자 · **환경 오염**
- 응답: 모양이 다름 · 키가 없음 · JSON 이 아님
- 네트워크: 차단(403) · 스로틀(429) · 서버 오류(5xx) · 없음(404) · 끊김
- 파일: 없음 · 손편집으로 형식이 깨짐
- **한 건 실패가 전체를 접지 않는가**
- **중간에 죽어도 앞서 모은 것이 남는가**

### 경계에서 꼭 보는 것

- 0건 · 1건 · 딱 꽉 참 · 상한 도달
- 뒤집힌 범위 · 음수 · 미래 날짜
- 보존 기간의 정확한 경계 (30일째 남고 31일째 빠지는가)
- 중복 입력이 합쳐지는가
- 재실행해도 결과가 안 불어나는가 (멱등성)

## 일반화를 검증한다

목록이나 규칙을 만들었으면, **그 목록을 만들 때 쓰지 않은 케이스**로 검증한다.
관측치로 만든 것을 관측치로 테스트하면 항상 통과한다 — 아무것도 증명하지 못한다.

```python
def test_BOUNDARY_korean_rule_generalizes_to_unlisted_collisions():
    """**한 번도 적어 둔 적 없는 복합어**로 규칙이 실제로 일반화하는지 본다."""
    never_listed = [
        ("가상화학 실험실 소프트웨어", "가상화"),
        ("컨테이너박스 재고 관리", "컨테이너"),
        ("머신러닝머신 판매", "머신러닝"),
        ("딥러닝쿠키 브랜드", "딥러닝"),
    ]
```

## 네트워크를 타지 않는다

테스트는 어디서든 같은 결과가 나와야 한다.

- 목록 API → `tests/helpers.py` 의 `FakeClient`
- HTTP 세션 → `FakeSession` · `FakeResponse`
- 상세 응답 → `fixtures/*.json` 에 떠 놓은 **실제 응답**
- 재시도 백오프 → `time.sleep` 을 무력화. 실제로 몇 초씩 기다릴 이유가 없다

**픽스처는 실제 응답을 떠서 쓴다.** 손으로 만든 가짜는 실제와 다른 모양이 되기 쉽다.

## 커버리지

```bash
../../.venv/bin/python3 -m coverage run --branch --source=lib,../_common tests/run.py
../../.venv/bin/python3 -m coverage report -m
```

**문장 커버리지 100% 를 기준선으로 둔다.** 지금 572/572 다.
분기는 도달 불가능한 방어가 남을 수 있다 — 그건 남겨 두고 이유를 적는다.

커버리지가 낮은 모듈은 대개 **production 에서 가장 중요한 경로**다.
`client.py` 는 처음 28% 였다. 403 차단 감지·재시도·백오프가 한 번도 실행된 적이 없었다.

**커버리지 100% 가 안전을 뜻하지 않는다.** 무엇을 못 잡는지 함께 적는다.

## 테스트가 구조적으로 못 잡는 것

보고서와 README 에 **명시한다.** 커버리지 숫자만 보고 안심하지 않게.

| 위험 | 왜 못 잡나 |
|---|---|
| 사이트가 API 를 바꾼다 | 떠 놓은 응답을 쓰므로 필드 이름이 바뀌어도 통과한다 |
| 차단 정책이 바뀐다 | 지금 아는 신호(UA)만 검증한다 |
| 새 오탐·누락 | 표본이 유한하다 |

이것들은 **정기 실행이 사실상 유일한 감시 수단**이다. 실행할 때 뜨는 실패 건수와
CSV 빈 칸이 신호다.

## 파일 구성

```
tests/
├── run.py           전부 모아 실행. 갈래별로 센다
├── helpers.py       FakeClient · FakeSession · 픽스처 로딩 · assert_raises
└── test_<모듈>.py    제품 모듈 하나에 테스트 파일 하나
```

**제품 모듈이 갈리면 테스트 파일도 갈린다.** 한 파일에 몰아 두면 무엇을 고쳤을 때
어디가 깨지는지 찾기 어렵다.

**새 파일은 `run.py` 의 `MODULES` 에 적어야 돈다.** 손으로 적는 목록이라 빠뜨리면 그
테스트가 **통과도 실패도 하지 않고 없는 것처럼 지나간다** — 실제로 열 건을 그렇게 잃었고,
개수만 보고는 알 수 없었다. 지금은 `run.py` 가 시작할 때 `tests/test_*.py` 와 목록을
대조해, 안 적힌 파일이 있으면 아예 안 돈다.

**`_common` 의 테스트는 `saramin/tests/` 에 있다.** 여섯이 함께 쓰는 코드라 어느 한
사이트에 붙여 두면 그 사이트를 지웠을 때 시험도 같이 사라진다.
