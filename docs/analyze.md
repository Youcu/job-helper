# 최종본으로 무엇을 분석하나

`csv/merged_career.csv` 를 **데이터 분석 자료로** 쓸 때 무엇을 물을 수 있고, 어떻게 재는지
적는다. 파이프라인 코드가 아니라 **분석의 설계**다.

## 먼저 — 거른 축은 분석 대상이 아니다

필터를 건 자리는 **분산이 없다.** 거기서 뽑은 "인사이트" 는 우리가 넣은 조건을 되읽는 것뿐이다.

| 죽은 축 | 왜 |
|---|---|
| `경력` | 전부 "신입 지원 가능". `신입 · 경력` · `경력무관` · `신입~5년` 은 **표기 차이**다 |
| `근무지` | `.env` 의 `HOME_LOCATIONS` 로 걸렀다 |
| 직무 | `.env` 의 `JOB_ROLES=백엔드,웹` 으로 걸렀다 |
| `Spring` · `FastAPI` 유무 | `CORE_TECH_STACKS` 로 걸러 **전부 있다** |
| `PHP` · `jQuery` 유무 | `EXCLUDE_TECH_STACKS` 로 걸러 **전부 없다** |
| `평점` 하한 | 2.9 미만이 잘린 **절단 분포**. "평점 낮은 곳은 어떻다" 는 못 한다 |
| `연봉` | 43건 중 **40건이 빈칸**. 표본이 아니다 |

그래서 `경력별 선호 기술스택` 같은 물음은 성립하지 않는다 (2026-09-14 사용자).

## 살아 있는 재료는 **두 칸의 글**이다

```
지원자격  = 기본역량 게이트   없으면 탈락
우대사항  = 경쟁력 게이트     있으면 앞선다
```

**데이터가 이미 2단 게이트로 나뉘어 있다.** 같은 기술이 공고마다 다른 단에 나오고,
그 비율이 **그 기술의 성격**이다. A·B 분석의 대부분이 이 구조 위에 선다.

---

# 공통 규칙

## 분모를 밝힌다

전체 43행이 아니다. 글이 빈 행이 있다.

```
지원자격이 있는 행  39
우대사항이 있는 행  34
```

비율을 낼 때 43 을 쓰면 틀린다.

## 고정 축을 뺀다

`Spring` · `Spring Boot` · `FastAPI` 는 **전부 있으므로** 세지 않는다. 세면 "43곳이 Spring 을
요구한다" 는 동어반복이 나온다.

## 기술 이름은 저장소의 정규화 엔진을 쓴다

`_common/skills.py` 의 `find_in_corpus()`. 사이트마다 다른 표기를 한 이름으로 모으고
(`Apache Kafka` → `Kafka`), 낱말 경계를 지킨다 (`Java` ≠ `JavaScript`). **새로 짜지 않는다.**

## 성격 판정

| 조건 | 성격 | 뜻 |
|---|---|---|
| 필수 ≥ 우대 × 2 | **기본기** | 없으면 탈락. 먼저 채워야 한다 |
| 우대 ≥ 필수 × 2 | **경쟁력** | 없어도 지원은 된다. **투자 대비가 좋다** |
| 그 사이 | 갈림 | 회사마다 다르다 |

배수 2 는 임의값이다. **43건에서는 1~2건 차이가 성격을 뒤집으므로**, 합이 5 미만인 항목은
표에 올리지 않는다.

## 표본이 43건이다 — 이것이 상한을 정한다

| 할 수 있다 | 못 한다 |
|---|---|
| 한 축의 빈도 · 상위 10개 순위 | 두 축의 교차 (평점 × 기술) |
| "절반이 넘는다" 같은 굵은 판단 | "37%" 같은 정밀한 비율 |
| 리프트 2배 이상의 뚜렷한 짝 | 리프트 1.2 수준의 미묘한 짝 |

교차 분석을 하려면 거르기 **전** 단계를 봐야 한다 (`history_read.csv` 754행). 다만 그건
"내가 지원할 수 있는 공고" 가 아니라 **시장 전체**라 물음이 달라진다.

# A. 무엇을 준비해야 하나 — 역량 지도

## A1 · 기술의 단 배치 — **가장 값어치 있다**

**무엇을** — 기술마다 `지원자격` 에 몇 번, `우대사항` 에 몇 번 나오는지.

**어떻게** — 두 칸의 글에서 각각 기술 이름을 뽑아 **행 단위로 중복을 없애고**(한 공고에서
`Java` 를 세 번 말해도 1) 센다. 위의 성격 판정을 건다.

**왜** — 입장권과 차별점을 가른다. 신입에게는 **경쟁력 쪽이 투자 대비가 가장 좋다** —
없어도 지원은 되는데 있으면 앞서기 때문이다.

## A2 · 동반 기술 빈도

**무엇을** — 고정 축을 뺀 기술이 몇 곳에 나오는지.

**어떻게** — `기술스택` 칸을 쓴다. 본문보다 넓다 — 사이트가 태그로 붙인 것까지 담는다.

**A1 과 묻는 것이 다르다.** A2 는 "얼마나 흔한가", A1 은 "필수인가 우대인가". `AWS` 는
20곳에 나오지만 **절반이 우대**라 성격이 다르다. 둘을 같이 봐야 뜻이 선다.

## A3 · 함께 오는 묶음

**무엇을** — 어떤 기술이 **짝으로** 오는가.

**어떻게** — 상위 22개로 좁히고 두 개씩 짝지어 함께 나온 횟수를 센다. 그냥 횟수로 보면
흔한 것끼리 무조건 높으므로 **리프트**로 고친다.

```
리프트 = 함께 나온 곳 / (A가 나온 곳 × B가 나온 곳 / 전체)
```

1.0 이면 우연, 2.0 이면 **우연의 두 배**로 함께 온다. 함께 5곳 미만은 버린다.

**왜** — 낱개로 공부할지 묶어서 할지를 정한다. `Docker + Kubernetes` 가 묶여 온다면
따로 배우는 것이 손해다.

## A4 · 계열 분기

**무엇을** — `Java/Kotlin` 계열과 `Python` 계열이 **다른 것을 요구하는가**.

**어떻게** — 각 공고를 태그로 계열에 넣고(둘 다면 "둘 다"), 계열마다 상위 기술을 센다.

**왜** — 어느 쪽을 팔지의 재료다. 두 계열이 같은 것을 요구하면 선택이 무의미하고,
다르면 갈라서 준비해야 한다.

## A5 · 요구 깊이

**무엇을** — 같은 기술도 `이해` / `사용 경험` / `구현` / `설계` / `최적화·운영` / `주도` 로
요구 수준이 갈린다.

**어떻게** — 동사·명사 묶음을 정규식으로 잡아 두 칸에서 각각 센다. 기술 이름과 무관하게
**문장의 격**을 본다.

**한계** — 정규식이라 `설계` 가 "DB 설계 경험" 인지 "설계도 검토" 인지 못 가린다. 굵은
경향만 읽고 **정밀한 비율로 쓰지 않는다.**

# B. 어떤 사람을 원하나 — 인재상

## B1 · 비기술 역량의 빈도와 단 배치

**무엇을** — `협업` · `학습` · `커뮤니케이션` · `주도성` · `AI 활용` 같은,
**기술 이름이 아닌** 요구.

**어떻게** — 표현이 흔들리므로 묶음으로 잡는다 (`협업|팀워크|동료와`). A1 과 같은 성격
판정을 건다.

**왜** — 자기소개서에서 무엇을 말해야 하는지가 나온다. 그리고 **어느 역량이 경쟁력 쪽인지**
알면 거기에 힘을 준다.

## B2 · 그 역량의 단 배치

B1 과 같은 표에서 함께 읽는다. `AI 활용` 이 우대 쪽이면 *"아직 필수는 아닌데 앞서는 자리"*
라는 뜻이고, 시점의 신호다.

## B3 · 표현 방식

**무엇을** — 공고가 `~하신 분`(사람 중심)으로 쓰는가 `~경험자`(이력 중심)로 쓰는가.

**왜** — 회사가 **무엇을 보는지**의 실마리다. 다만 이건 가장 약한 신호이고, 문체의 유행일
수도 있다. **참고로만 본다.**
